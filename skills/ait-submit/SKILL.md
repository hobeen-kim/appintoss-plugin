# 앱인토스 제출 가이드

제출 전 최종 검수를 실행하고, Developer Center 콘솔에 입력할 출시 노트와 기능 목록을 `docs/SUBMIT.md`에 정리한다.

## 2-문서 규칙 (APP-SPEC + SUBMIT)

**두 문서의 역할을 분리한다.**

- **`docs/APP-SPEC.md`** = 앱 전체 정보 마스터(superset). 작업 완료 후 생성. 앱 기본 정보·수익 모델·기술 스택·스토어 노출 정보·제출 에셋·출시/업데이트 노트·앱 내 기능(전체)·광고 노출 트리거 명세·푸시 상세·토스 로그인 설정·검수 안내·검수 전 자가점검 요약·업로드 절차를 모두 포함한다.
- **`docs/SUBMIT.md`** = 콘솔 제출용 최소 문서(부분집합). **오직 두 섹션만 포함한다**:
  1. **출시 노트 / 업데이트 노트**
  2. **앱 내 기능** (한국어 기능 이름 / 영어 기능 이름 / 이동 URL)
- 그 외 모든 항목(스토어 노출 정보·제출 에셋·토스 로그인 설정·업로드 절차·검수 안내·검수 전 자가점검 요약·스마트발송·앱 정보표·콘솔 대조)은 **SUBMIT에 두지 않고 APP-SPEC.md에만 둔다.**
- 두 문서가 충돌하면 **APP-SPEC이 우선**한다.

**APP-SPEC.md에 작성하는 항목** (SUBMIT에서 제외 — 마스터에만 존재):

1. **앱 기본 정보**: 앱명(콘솔 등록정보와 일치 — 불일치는 반려 사유), 카테고리 추천 1순위 + 대안 1, 상세설명. 수익 모델·기술 스택 포함
2. **스토어 노출 정보**: 부제(20자)·상세 설명(200~500자)·카테고리(**콘솔 대/중/소 3단 전체 경로**)·검색 키워드(10개). **부제·상세 설명의 허용 특수문자는 `:` `·` `?` 뿐이다** — `■`·`-`·`※` 등은 콘솔 저장 시 "특수문자는 :, ·, ? 만 사용할 수 있어요"로 반려된다(실측). 불릿은 `·`로 쓰고 줄바꿈으로 구분한다
3. **제출 에셋**: 아이콘 600×600 · 화면예시 636×1048 ×3 · 썸네일 1932×828 상대경로 + 미리보기 임베드
4. **토스 로그인 콘솔 설정**: 동의항목표·콜백·약관 URL (로그인 사용 앱만)
5. **업로드 절차**: `.ait` 경로·버전, `ait deploy -m "출시메모"` 옵션(SDK 2.3.0), 앱 정보 등록 간소화(2026-05-11 콘솔 변경 — 등록 시 최소 정보만 입력) 반영
6. **검수 안내**: 검수 4단계(운영/디자인/기능/보안)·**앱 정보 검토 영업일 1~2일 / 앱 번들 검토 영업일 최대 3일(카테고리에 따라 7일 이상)**, **앱 정보 검수와 코드 검수는 별개 단계**(앱 정보 검토가 끝나야 출시 가능), 검토 요청은 한 번에 한 버전만·테스트 1회 이상 완료 필요, 잘못 제출하면 '요청 취소하기'로 회수, 자동 검수 오탐 시 채널톡 수동 승인 경로
7. **검수 전 자가점검 요약**: REVIEW-REPORT(검수 체크리스트 결과) 링크
8. **스마트발송(선택)**: 스마트발송을 사용하는 앱만. 캠페인 제목(7자)·메시지 제목(7자)·내용(25자, "~요." 마침표 — "토스에서" 미포함, 사용자 지시 2026-06-12) 작성안, 발송 유형(일회성/상시·반복), 타겟 세그먼트, 랜딩 URL
9. **광고 노출 트리거 명세·푸시 상세·앱 내 기능(전체 화면 동작 상세)** — APP-SPEC 전용 헤비 섹션
10. **세그먼트 설계** (3개 이상 필수) — 카테고리 4종(거래 정보·유저 정보·유저 활동·유저 프로파일), AND/OR 조합, 예측형 정확도 50% 이상 권장 (출처: https://developers-apps-in-toss.toss.im/segment/intro.html)
11. **스마트발송 캠페인 설계** (추천 문구 포함) — 캠페인·타겟 세그먼트·랜딩 URL·발송 기간 + 추천 문구(제목 ≤7자·본문 ≤25자 "~요.") (출처: https://developers-apps-in-toss.toss.im/smart-message/intro.html)

## 실행 순서

### 1단계: ait-review 검수 실행

`ait-review` 스킬의 11단계 체크리스트를 실행한다. 하나라도 실패하면 제출을 중단하고 수정 사항을 안내한다.

### 2단계: docs/APP-SPEC.md · docs/SUBMIT.md 읽기 또는 생성

프로젝트의 `docs/APP-SPEC.md`를 읽는다. 파일이 없으면 `references/app-spec-template.md` 템플릿으로 새로 생성한다.
`docs/SUBMIT.md`도 읽는다. 파일이 없으면 `references/submit-template.md` 템플릿으로 새로 생성한다.

**기존 프로젝트 마이그레이션 (구 형식 SUBMIT.md 감지 시)**

`docs/SUBMIT.md`가 이미 존재하고 "출시 노트/업데이트 노트"·"앱 내 기능" 이외의 섹션(스토어 노출 정보·제출 에셋·토스 로그인 설정·업로드 절차·검수 안내·검수 전 자가점검 요약·스마트발송·앱 정보표·콘솔 대조 등)을 포함하면 = **구 단일파일 형식**이다. 이 경우 슬림화 전에 **반드시** 다음을 수행한다 (데이터 유실 금지):

1. `docs/APP-SPEC.md`가 없으면 `references/app-spec-template.md`로 생성한다.
2. 구 SUBMIT.md의 **모든 섹션 내용을 APP-SPEC.md의 대응 섹션으로 그대로 이관**한다 — 코드에서 재생성 불가한 손수 작성분(부제·검색 키워드·상세 설명·로그인 동의 항목표·스마트발송 캠페인/메시지 문구·에셋 경로·**업데이트 노트 누적 history 전체**)을 빠짐없이 옮긴다.
3. 신규 헤비 섹션(수익 모델·기술 스택·광고 노출 트리거 명세·푸시 상세·앱 내 기능 전체 동작 상세)은 코드베이스에서 추가로 채운다.
4. 그 후 SUBMIT.md를 "출시/업데이트 노트 + 앱 내 기능" 2개 섹션만 남기고 슬림화한다. **업데이트 노트 누적 history는 두 문서 모두에 보존**한다.
5. 이관 완료 후 APP-SPEC와 SUBMIT 사이에 누락 섹션이 없는지 교차 확인한다.

### 3단계: APP-SPEC.md 전체 채우기 → SUBMIT.md 최소 작성

APP-SPEC.md(전체 마스터)를 먼저 모두 채운 뒤, 그중 **출시/업데이트 노트와 앱 내 기능 두 섹션만** 추려 SUBMIT.md(콘솔 최소 문서)에 작성한다. 그 외 항목(스토어 노출 정보·제출 에셋·토스 로그인·업로드 절차·검수 안내·자가점검·스마트발송)은 SUBMIT에 넣지 않고 APP-SPEC에만 둔다.

**APP-SPEC 전용 섹션 채우기 지침**:
- **수익 모델**: PLAN.md의 수익 모델 결정 내용을 기반으로 광고·인앱·제휴 비중과 AdMob/토스애즈 비중을 기록한다.
- **기술 스택**: `package.json`·`apps-in-toss.config.ts`에서 프레임워크 버전, 사용 SDK·플러그인, 외부 연동 항목을 추출해 기록한다.
- **광고 노출 트리거 명세**: 코드베이스(광고 호출 지점)를 분석하여 사용자 행동별 노출 광고 유형·빈도·쿨다운을 표로 기록한다. 광고 미사용 시 '광고 없음' 표기.
- **푸시 / 스마트발송 상세**: 스마트발송 사용 앱이면 전체 발송 계획(유형·트리거·타겟·메시지)을 기록한다. 미사용 시 '발송 없음' 표기.
- **앱 내 기능 (전체)**: 콘솔 3개 제한과 무관하게 모든 화면·기능을 화면 흐름/상태/동작 컬럼까지 채워 기록한다.

**문서별 채우기**

아래 정보를 코드베이스에서 자동으로 수집하여 채운다. 별도 표기가 없으면 **APP-SPEC.md에만 작성**하고, **SUBMIT.md에는 "출시/업데이트 노트"와 "앱 내 기능"만** 작성한다.

#### 스토어 노출 정보 (부제·상세 설명·카테고리·키워드) — APP-SPEC.md에 작성
- **부제**: 서비스 성격이 한눈에 이해되게 간결히. **느낌표(!)·비속어 금지**, 과장 금지. 작성 규칙은 `references/submit-store-guide.md` 참조
- **상세 설명**: 사용자 관점 — 경험할 수 있는 내용을 구체적으로(핵심 기능·시나리오·차별점). 카피 보이스 일관. **"~없습니다/안 됩니다" 부정 나열·방어적 프라이버시 고지 금지**(출시 노트 톤 규칙과 동일). 금지: 과장, 금융상품 추천성 문구, 외부 서비스·앱 설치 유도. 규칙: `references/submit-store-guide.md`
- **카테고리**: `references/categories.md`의 **선택 가능 항목만** 사용. PLAN.md 주제·타겟 기반 **2개 추천**(1순위 + 대안), 소분류 있으면 '대분류 · 소분류'로. 금융 그룹은 선택 불가
- **검색 키워드**: 타겟 사용자가 검색할 단어 10개

#### 출시 노트 (create — 최초 1회) — APP-SPEC.md + SUBMIT.md 둘 다 작성
- Developer Center 콘솔의 **"빠른 검토를 위해, 앱의 주요 화면과 기능을 간단히 소개해주세요."** 항목에 입력할 내용
- 코드베이스(라우터, 페이지 컴포넌트)를 분석하여 앱의 주요 화면과 기능을 소개하는 글 작성
- 변경사항 나열이 아니라 **앱 전체를 처음 보는 검수자에게 앱을 소개**하는 방식으로 작성
- 한국어로, 3~6줄 이내
- create·update 무관하게 "출시 노트" 섹션은 최초 작성본을 유지(앱 소개는 변하지 않으면 그대로)

**톤 규칙 (중요 — 자연스럽게)**:
- **"~하지 않습니다 / ~없습니다 / ~안 됩니다" 부정·방어 문구를 나열하지 마라.** 정책 준수(금융상품 추천 없음·외부 송금 없음·앱 설치 유도 없음 등)는 코드와 검수가 보장하므로, 출시 노트에 변명처럼 적지 않는다.
- **프라이버시·저장 방식을 강박적으로 반복하지 마라.** "기기에만 저장/서버 미전송"은 그것이 앱의 **핵심 차별점일 때만 1회**, 사용자 가치 표현으로(예: "기록은 내 폰에만 안전하게 남아요") — 검수 회피용 고지처럼 쓰지 않는다.
- 무엇을 **해주는지**(사용자 가치·핵심 사용 흐름) 중심으로, 사람이 앱스토어 소개글 읽듯 자연스럽게. 기능 메커니즘(가중 합산·데이터 건수 등)은 1줄로 충분.
- 좋은 예 결: "결혼식·장례·돌잔치에서 얼마를 내야 할지 고민될 때, 관계와 상황을 고르면 적정 금액을 알려드려요. 낸 금액은 따로 기록해 다음에 참고할 수 있어요."

#### 업데이트 노트 (update — 버전별 누적) — APP-SPEC.md + SUBMIT.md 둘 다 작성
- **create·update 모두** APP-SPEC.md와 SUBMIT.md에 "업데이트 노트" 섹션을 유지한다.
- update 실행마다 **최신 버전 항목을 맨 위에 추가**한다(`### v{버전} ({일시})` + 변경 1~3줄). **기존 버전 노트는 삭제하지 않고 아래에 누적 보존.**
- 사용자 관점으로 이번 버전에서 달라진 점만. 과장·금지표현 불가.
- create 최초 생성 시에는 `### v{초기버전} (최초 출시)` 한 줄로 시작.
- 이 내용은 update 보고서(REPORT) §3-1 업데이트 노트와 동일하게 맞춘다.

#### 제출 에셋 임베드 — APP-SPEC.md에 작성
- `docs/assets/`의 아이콘(icon.png 600×600)·화면예시 3장(screenshot-1~3.png 636×1048)·썸네일/배너(thumbnail.png 1932×828)를 APP-SPEC.md "제출 에셋" 표에 **상대경로 + 미리보기 임베드**(`![](assets/파일명)`)로 기록한다.
- 에셋 파일이 없으면 해당 행에 "미생성" 표기(조용한 누락 금지). 규격은 sips 실측값을 함께 적는다.

#### 토스 로그인 설정 (로그인 사용 앱만) — APP-SPEC.md에 작성
- 로그인을 쓰는 앱은 APP-SPEC.md에 "토스 로그인 설정" 섹션을 추가한다. `ait-login/references/oauth-consent-guide.md` 기준.
- **동의 항목 추천표**(항목·scope·필수/선택/사용안함·근거) + **콜백 필수 여부 자동 판정**(이름·이메일·성별 외 항목 켜면 필수) + **약관 URL**(서비스 이용약관 필수·개인정보 처리방침, `docs/legal/` 생성 후 서버 정적 라우트 URL 또는 '호스팅 필요' 상태).
- 로그인 미사용 앱은 이 섹션 생략.

#### 앱 내 기능 목록 — APP-SPEC.md + SUBMIT.md 둘 다 작성
- 라우터 설정(react-router-dom)에서 페이지 경로를 추출
- 각 페이지의 실제 역할을 코드에서 파악

- 공식 규격(2026-06-10 공홈 확인 — https://developers-apps-in-toss.toss.im/development/test/function.html):
  - 검색 결과·미니홈에서 특정 기능으로 **바로 진입(홈을 거치지 않음)**하게 하는 항목
  - **한국어 기능 이름**: 최대 10자, 허용 특수문자 `:` `.`만, 이모지 불가, "~하기" 또는 명사형
  - **영어 기능 이름**: 최대 15자, 허용 특수문자 `:` `.`만, 이모지 불가, 첫 글자만 대문자
  - **이동 URL**: `intoss://{appName}/경로` (`appName`은 `apps-in-toss.config.ts`에서 읽음, 홈은 `/`, 쿼리 파라미터 가능). 출시 전 테스트는 `intoss-private://{appName}?_deploymentId={업로드 시 발급}` 스킴을 쓴다 — `intoss://`는 정식 출시 후에만 열린다
  - **최소 1개 필수**(비게임), URL 미접속 시 반려, 검토는 영업일 1~2일 소요

- **유저 문의 조회**: 앱인토스 콘솔 좌측 문의 내역 메뉴에서 문의 유형·내용·기기 정보 확인 가능

- **자동 푸시**: 답변 작성 시 유저에게 자동으로 푸시 알림 발송
- 고객센터 답변은 콘솔 수동 기능이며 API 자동화는 제공되지 않음

#### 스마트발송 (상세 — 마케팅 발송 사용 시) — APP-SPEC.md에 작성

스마트발송을 사용하는 앱만 이 섹션을 작성한다. 사용하지 않으면 섹션을 생략한다.

- **스마트발송 = 광고성 전용**: 할인·이벤트·신규 상품 안내 등 광고성 메시지에만 사용 가능. 결제·배송·환불 등 기능성 정보는 스마트발송으로 발송 불가.
- **발송 유형을 반드시 명시**: 일회성(원타임) 인지 / 상시·반복 인지.
- **메시지 작성안을 공식 규칙대로 자동 생성**:
  - 캠페인 제목: 7자 이내(공백 포함), 명사형
  - 메시지 제목: 7자 이내(공백 포함), 명사형
  - 메시지 내용: 25자 이내(공백 포함), "~요." 형식, "토스에서"/"토스"는 넣지 않는다(공홈은 포함 권장이나 사용자 지시 2026-06-12로 미사용)
- **타겟 세그먼트**: 마케팅 수신 동의 사용자 중 세그먼트 명시
- **랜딩 URL**: 정상 접속 확인 필수. 소재별 상이 설정 불가 — 캠페인 내 모든 소재에 동일한 URL 사용
- 상세 작성 규칙은 `ait-smart-message` 스킬 참조
