# 푸시 알림 마케팅 소재 가이드

> **사용자 직접 수행 영역과 적극 추천 의무**: 알림동의문 등록·캠페인 생성·테스트 발송(test-send) 등 푸시알림 설정·발송은 사용자가 콘솔에서 직접 수행한다 — 콘솔 설정·발송을 자동화하지 않는다. 테스트 발송(test-send)도 사용자가 콘솔에서 직접 수행한다(보고서 §🙋 사용자가 해야 할 것 체크리스트로 안내). 에이전트는 **세그먼트·캠페인·문구 설계를 적극 추천·산출**하고(create/update 시 APP-SPEC.md 세그먼트 설계·스마트발송 캠페인 설계 섹션 필수), 콘솔 등록·발송 수행만 사용자가 직접 한다. 클릭 유도 문구는 `knowledge/copy-deliberation.md` 절차(다중 에이전트 의논)를 따른다. (사용자 지시 2026-06-11, 2026-06-12)

## 광고성 vs 기능성 구분

스마트발송은 **광고성 메시지 전용**이다 — 기능성은 별도 콘솔 발송(아래 절 참조).

| 구분 | 목적 | 예시 | 검수 | 발송 경로 | 제한 |
|------|------|------|------|-----------|------|
| 광고성 | 마케팅·프로모션 | 할인 이벤트, 신규 상품 홍보, 캠페인 프로모션 | 스마트발송 검수(최대 3영업일) | 스마트발송(콘솔) | 마케팅 수신 동의 사용자만 |
| 기능성 | 서비스 필수·사용자 선택 알림 | 결제 완료, 배송 현황, 재입고 알림, 이벤트 시작 알림 | 소재 검토 승인 | 콘솔 직접 발송(서버 불필요) | 사전 알림 동의 등록(콘솔 기능) 선행 필요 |

기능성(서비스 필수 정보) 알림은 스마트발송으로 발송할 수 없다.

### 두 경로의 고유 가치 (실측 사례)

> 출처: 앱인토스 공식 웨비나 2026-08-21. 성장 관점 전체는 `ait-analytics/references/growth-playbook.md`.

| 구분 | 고유 가치 | 실측 성과 |
|---|---|---|
| **광고성** | **내 앱을 한 번도 쓴 적 없는 유저에게 도달하는 유일한 무료 수단.** 토스 푸시로 나가므로 별도 광고비가 들지 않는다 | 클릭 500회 사례 — "이것만 잘 써도 1,000명은 들어오게 할 수 있다" |
| **기능성** | 유저 **동의·행동 기반**이라 갑작스러운 광고보다 클릭률이 훨씬 높다 | 이탈 유저 복귀 **약 40%**(3만 발송 → 1만+ 복귀), 주간 리텐션 알림 **CTR 약 60%**(5만 발송 → 3만 클릭) |

- **둘 다 무료다.** 초기 유입이 없는 상태에서 가장 먼저 써야 할 채널이며, 실측 사례에서도 출시 후 15일간 반응이 없다가
  광고성 스마트 발송을 시작하면서 **500명 단위 유입 스파이크**가 발생했다.
- 스파이크를 **반복**하면 평균 유입 기준선 자체가 계단식으로 올라간다.

## 기능성 메시지 (콘솔 발송)

2026-05-28 변경 사항: 기존에는 서버 연동을 통해서만 기능성 메시지를 발송할 수 있었으나, 이제 콘솔에서 직접 발송 가능하다. (출처: https://toss.im/apps-in-toss/blog/update-26-5-28)

### 광고성 vs 기능성 콘솔 입력 필드 비교

| 입력 항목 | 광고성 (스마트발송) | 기능성 (콘솔 직접 발송) |
|-----------|-------------------|------------------------|
| 캠페인 제목 | 필수 (7자 이내) | — |
| 메시지 제목 | 필수 (7자 이내) | 필수 (7자 이내) |
| 메시지 내용 | 필수 (25자 이내, "~요." 마침표) | 필수 (25자 이내, "~요." 마침표) |
| 이동 URL | 필수 | 필수 |
| 타겟 세그먼트 | 필수 (마케팅 수신 동의 사용자) | — |
| **동의문 이름** | — | **필수** (콘솔 → 스마트발송 → 알림동의문에서 등록한 이름) |
| **알림 발송 시점** | AI 자동 최적화 (사용자 직접 설정 불필요) | **필수** (일회성·정기 발송 중 선택 및 시점 지정) |

> 기능성 메시지는 **동의문 이름**과 **알림 발송 시점**을 콘솔에서 직접 입력해야 한다. 광고성 메시지의 AI 자동 발송 일정과 혼동하지 않도록 주의한다.

### 선행 조건 — 알림 동의 등록

기능성 메시지 발송 전에 **알림 동의 등록(콘솔 기능)** 이 완료되어 있어야 한다.

- 콘솔 경로: 워크스페이스 → 미니앱 → 스마트 발송 → **알림동의문** 탭
- 결제 완료·배송 시작 등 거래 필수 정보는 동의문 불필요. 재입고 알림·이벤트 알림 등 사용자가 명시적으로 신청한 선택적 알림은 동의문 필요.

#### 알림동의문 등록 화면 입력 항목 (콘솔 실측 2026-08-28)

`알림동의문 노출 화면` 섹션의 입력 항목은 두 개다.

| 입력 항목 | 형태 | 선택·작성 기준 |
|---|---|---|
| **알림 발송 방법** | 라디오 2택 | 사용자마다 시점이 다른 **개인화 알림 → `특정 조건이 충족되면 직접 보내요.`**<br>전체에게 같은 때 보내는 알림 → `정해진 요일과 시간에 보내요.` |
| **화면 제목** | 필수 텍스트 | 동의 화면 헤드라인. 질문형으로 쓴다 (예: `~ 알려드릴까요?`) |

> **`알림 발송 방법` 선택은 앱 설계에 직결된다.** 개인화 알림인데 `정해진 요일과 시간`을 고르면 전체 공통 발송이 되어 설계가 어긋난다. 앱 기획 단계에서 어느 쪽인지 먼저 확정하고 등록을 안내한다.
>
> 공홈(`guide/marketing/smart-message`)은 `알림 동의문 이름`·`알림 발송 시점`·`알림 발송 방법` 3항목으로 적고 있으나, **실제 콘솔 화면은 `화면 제목`이라는 필수 필드를 따로 갖는다**(항목명 불일치 — 콘솔 실측이 기준).

#### 등록 후 — `templateCode` 받기

등록하면 템플릿 코드가 발급된다. **콘솔 → 스마트 발송 → `기능성` 탭**에서 확인한다 — **알림동의문 탭이 아니다**(출처: 공홈 `guide/marketing/smart-message`). 이 값이 없으면 SDK로 알림 동의를 아예 요청할 수 없다.

**코드 연동 함수**: `Notification.requestAgreement`
`requestNotificationAgreement`는 **deprecated**다(`@apps-in-toss/web-framework@3.1.1` 타입 정의 — "이 함수는 더 이상 사용되지 않아요. `Notification.requestAgreement`를 사용해주세요.", Toss Android/iOS 5.255.0 이후).

```tsx
import { Notification } from '@apps-in-toss/web-framework';

const cleanup = Notification.requestAgreement({
  options: { templateCode: '<콘솔 → 스마트 발송 → 기능성 탭에서 확인한 코드>' },
  onEvent: ({ type }) => {
    // 'newAgreement' | 'alreadyAgreed' | 'agreementRejected'
  },
  onError: (e) => {},
});
// 반환되는 cleanup 으로 콜백 해제 — 미호출 시 리스너 중복 등록·메모리 누수
```

파라미터·이벤트 상세는 `ait-sdk/references/ait-interaction.md` 참조.

### 발송 방법

- 콘솔에서 "토스에게 발송 요청하기" 기능으로 직접 발송 (서버 개발·토스 로그인 연동 불필요)
- 콘솔 경로: 워크스페이스 → 미니앱 → 스마트 발송 → 캠페인 생성
- 메시지 제목·내용·이동 URL 작성 → 소재 검토 승인 후 활성화
- 일회성 또는 정기 발송 선택 가능. 단 **정기 발송의 주기는 전체 공통**으로만 설정된다:
  - **매일** — 매일 지정한 시간에 발송 / **매주** — 원하는 요일과 시간을 선택해 발송
  - 시작일·종료일 설정, `종료일 없음` 선택 시 직접 중단할 때까지 계속 발송
- **"토스에게 발송 요청하기" 경로는 이름 변수만 사용할 수 있다.** 임의 변수 치환은 서버 API(`context`)에서만 가능하다.
- **판정: 사용자마다 다른 날짜·시점에 보내야 하면 콘솔 정기 발송으로는 불가능하고 서버 API가 필수다.** (D-day 알림, 개인 스케줄 리마인드 등) — "정기 발송이 되니 서버 없이 가능하다"는 판단은 틀렸다. 이 판정은 앱의 서버 필요 여부를 바꾸므로 기획 단계에서 먼저 확정한다.
- **테스트 발송**: 테스트 발송(test-send)은 사용자가 콘솔에서 직접 수행한다(보고서 §🙋 사용자가 해야 할 것 체크리스트로 안내). 기능성 템플릿 심사 대기는 `ait-console template-watch`가 심사 통과를 자동 감시하고 완료 시 알림을 제공한다.

## 기능성 알림 설계 — 무엇을, 언제 보낼 것인가 (실측)

문구보다 **어느 지점에, 몇 분 뒤, 무슨 요일 몇 시에 보내는가**가 성과를 가른다.

### 유형 A — 이탈 지점 처방 (퍼널 복구)

앱을 벗어나 대기해야 하는 구간이 있으면 **그 대기 시간에 맞춰** 알림을 예약한다.

- 실측 사례: 외부 앱에서 데이터를 받아오는 데 10~15분이 걸려 유저가 잊고 돌아오지 않았다
  → **"15분 뒤에 알림을 보내 드릴게요, 받으시겠습니까?"** 로 동의를 받고 도착 시점에 발송
- 결과: **복귀율 약 40%**, 해당 구간 전환 **+14%p**, 최종 전환 **9% → 14%**
- 전제: **로그로 최대 이탈 구간을 먼저 특정**해야 한다(`ait-analytics`). 앞뒤 구간을 함께 바꾸면 효과를 분리할 수 없다.

### 유형 B — 재방문 이유 만들기 (리텐션)

단건 소비형 앱은 "한 번 쓰고 끝"이 되기 쉽다. **주기적으로 볼 이유**를 알림으로 만든다.

- 실측 사례: "이번 주 팔로우 변화를 보실래요?" 를 **유저가 여유로운 토요일 오전**에 발송 → **CTR 약 60%**
- **발송 시점(요일·시간대)까지 설계 대상**이다. 문구만 다듬고 시점을 방치하면 CTR이 나오지 않는다.
- 앱 성격에 맞는 주기를 잡는다 — 변화가 쌓이는 데 걸리는 시간이 곧 발송 주기다.

> 개인별로 시점이 다른 알림은 **콘솔 정기 발송으로 불가능**하다(주기가 전체 공통). 아래 「서버 직접 API 발송」이 필수다.

## 서버 직접 API 발송 (기능성 메시지)

콘솔 발송이 추가된 뒤에도 **서버 직접 발송 경로는 그대로 존재한다.** 개인화 시점 발송·임의 변수 치환은 이 경로만 가능하다.

**Base URL**: `https://apps-in-toss-api.toss.im`

| 용도 | 엔드포인트 | 요청 한도 |
|---|---|---|
| 단건 발송 | `POST /api-partner/v1/apps-in-toss/messenger/send-message` | 앱당 분당 15,000회 · **사용자당 분당 10회** |
| 대량 발송 | `POST /api-partner/v1/apps-in-toss/messenger/send-bulk-message` | 앱당 분당 3,000회 |
| 테스트 발송 | `POST /api-partner/v1/apps-in-toss/messenger/send-test-message` | 앱당 분당 3,000회 |

- **인증**: mTLS 클라이언트 인증서(CN으로 미니앱 식별) + 사용자 인증 토큰(메시지 전송 scope). 인증서 발급·IP 대역은 `back-api/references/ait-server-api.md` 참조.
- **본문**: `{ "templateSetCode": string, "context": object }` — `context`로 임의 변수를 치환한다(콘솔 발송의 이름 변수 한정과 다른 지점).
- **오류**: HTTP는 **200**으로 오고 `resultType: "FAIL"`로 판별한다.

| 코드 | 의미 |
|---|---|
| `5004` | 승인되지 않은 메시지 템플릿 |
| `4034` | 워크스페이스 권한 없음 |
| `4010` | 인증 정보 없음 |
| `4095` | 요청 한도 초과 |

> **선행 조건**: 기능성 푸시와 알림, 프로모션, 토스페이를 쓰려면 **토스 로그인을 반드시 연동**해야 한다(공홈). 로그인 연동은 `ait-login` 스킬.

## 메시지 작성 규칙 (공식)

### 캠페인 구성 요소

| 항목 | 규칙 |
|------|------|
| 캠페인 제목 | **7자 이내(공백 포함), 목적이 드러나는 제목** |
| 캠페인 그룹 이름 | 발송 목적·실험 의도를 표현 |
| 메시지 제목(광고성) | **7자 이내(공백 포함), ~하기/명사형** |
| 메시지 제목(기능성) | **7자 이내(공백 포함), 명사형** |
| 메시지 내용 | **25자 이내(공백 포함), 문장형 "~요." + 마침표 필수** |
| 비게임 앱 | **"토스에서" 미포함** — 공홈 가이드는 포함을 권장하나 사용자 지시(2026-06-12)로 쓰지 않는다 |
| 게임 앱 | 메시지에 **"게임"** 단어 명시 (파생 장르명·전문용어 금지 — "퍼즐 게임", "액션 게임" 등 직관적 장르명 사용) |
| 변수 처리 | 변수는 **2글자로 간주** |
| 제목-본문 연결 | 제목은 그 자체로 완성된 단어/문장, 제목-본문이 자연스럽게 연결되어야 함 |
| 타겟 | 마케팅 수신 동의 사용자 + 세그먼트로만 발송 |
| 캠페인 중복 금지 | 동일 마케팅 목적으로 다중 캠페인 생성 금지 (어뷰징 간주) |
| 발송 한도 | 워크스페이스당 10만 건 |

### 금지 표현

다음 표현이 포함된 문구는 검수 거절 사유가 된다:

- **은어·밈**: 유행어, 인터넷 신조어
- **특정인 이름**: 연예인·유명인 등 실명 언급
- **과장된 광고성 표현**: "지금 바로!", "초특가!", "역대급", "긴급!", "대박", "무조건", "100%" 등
- **불안감 조성**: "지금 안 하면 손해", "마지막 기회", "놓치면 후회" 등
- **느낌표·이모지**: 모든 형태 금지
- **띄어쓰기 생략**: 글자수 맞추려 붙여 쓰는 행위
- **어색한 조사 생략**: 자연스러운 문장이 되어야 함

## CTR 최적화 — AI 자동 최적화

AI(Machine Learning)가 **pCTR(예측 클릭률) 기반**으로 고관여 사용자를 예측하고, 클릭이 잘 되는 발송 시간을 자동으로 최적화한다. 발송 시점과 타겟 선정은 AI 자동 최적화가 기본이다.

## 발송 메커니즘

### 발송 흐름

스마트발송은 **테스트 발송 → 본 발송** 순으로 진행된다.

**테스트 발송**은 파트너사가 하는 테스트가 아니라, **앱인토스 내부에서 AI 학습을 위해 자동으로 진행하는 발송**이다.
- 설정한 세그먼트의 pCTR로 서비스 고관여자를 예측하고, 최적의 대상·발송 시점을 탐색한다.
- **최대 7일**간 진행되며, **클릭 25건 또는 발송 2,500건** 중 하나를 채우면 즉시 본 발송으로 넘어간다.

**본 발송**은 테스트 결과를 반영해 자동 최적화된 상태로 나간다.

### 발송 한도·조건 (공홈)

- **워크스페이스(사업자)당 10만 건**까지 발송할 수 있다.
- **재방문 유도 캠페인은 발송 시작일 기준 직전 30일간 사용자가 100명 이상**이어야 발송할 수 있다. 신규 앱은 이 조건 때문에 초기에 재방문 캠페인을 못 쓴다 — 신규 유입 캠페인부터 설계한다.
- 광고성 캠페인은 그룹당 **소재 2개(a안·b안)**까지 등록할 수 있고, **동적 변수(`#{이름}` 등)를 쓸 수 없다**(기능성 API 발송에서는 변수 사용 가능, 변수는 2글자로 계산).
- 푸시 내용을 작성하면 **알림 메시지에 자동 반영**된다.
- 템플릿 문구 검수가 필요하다(광고성은 자동 검수). 문구 검토에서 알림 동의문이 필요하다고 반려되면, 동의문을 구성한 뒤 재검토를 요청한다.
- 사용자가 알림 수신을 해제할 수 있는 기능과 안내를 제공하는 것이 권장된다(토스 앱 > 전체 탭 > 설정 > 알림 > 서비스별 알림).

### 활성화 시간대별 자동 일정

| 활성화 시각 | 테스트 발송 | 본 발송 |
|-------------|------------|---------|
| 00:00 ~ 04:59 | 당일 08:00 | 당일 15:00 |
| 05:00 ~ 11:59 | 당일 15:00 | 다음날 08:00 |

### 발송 기간 설정 기준

- 검수 최대 **3영업일** + 테스트 발송 최대 **7일**을 고려해 발송 기간을 설정한다.
- 발송 기간이 짧으면 검수·테스트 완료 전 기간이 만료될 수 있으니 여유 있게 설정한다.

### 어뷰징 주의

동일한 마케팅 목적으로 여러 캠페인을 생성하면 **어뷰징으로 간주**된다. 하나의 목적에는 하나의 캠페인을 사용한다.

## 세그먼트 타겟팅

출처: https://developers-apps-in-toss.toss.im/segment/intro.html

스마트발송 타겟은 마케팅 수신 동의 사용자 중 **세그먼트**로만 선택한다. 세그먼트는 콘솔에서 조건 기반으로 유저 그룹을 생성한다. 콘솔 등록은 사용자 직접 수행.

토스는 실제 결제 데이터 기반 100+개 카테고리로 무료 타겟팅 가능.

> **유저 활동 조건은 미니앱 '로그인'이 아니라 '접속' 기준으로만** 설정할 수 있다.

### 조건 카테고리 4종

| 카테고리 | 포함 항목 |
|---------|---------|
| 거래 정보 | 브랜드·광고 카테고리·토스페이 사용 여부 |
| 유저 정보 | 나이·성별·신용점수·앱 버전·통신사·지역 |
| 유저 활동 | 앱 내 행동 이력 (미니앱 접속 기준) |
| 유저 프로파일 | 금융 성향·라이프사이클·관심사 추정 |

- 여러 조건은 **AND/OR 조합** 가능
- **예측형 세그먼트**: 정확도 설정 필수 — 일반적으로 **50% 이상 권장** (정확도↑ = 모수↓)
- 세그먼트명은 **삭제 후 재사용 불가** — 신중히 명명
- **즐겨찾기**로 저장하면 푸시·알림·스마트 발송에서 바로 선택할 수 있다
- **고정된 모수로 저장**하면 저장 시점의 모수가 고정된다(최신화되지 않음) — 목적에 맞게 고른다
- 타겟 샘플링으로 세그먼트 인원 수를 조정할 수 있다
- 여러 조건은 **AND / OR**로 조합한다. 조합하면 하나의 세그먼트로 합쳐지고, '되돌리기'로 다시 분리할 수 있다
- **즐겨찾기 설정** 시 푸시·알림·스마트발송에서 바로 사용 가능

### APP-SPEC 세그먼트 설계 연계

create/update 시 **APP-SPEC.md 세그먼트 설계 섹션(3개 이상)** 을 필수 작성한다. 스마트발송 캠페인 설계에서 이 세그먼트를 타겟으로 지정한다.

### 주요 세그먼트 활용

| 세그먼트 | 타겟팅 키워드 예시 | 적합한 앱 |
|---------|-----------------|---------|
| 커피 소비자 | "커피 자주 마시는" | 카페 추천, 쿠폰 |
| 1인가구 | "혼자 사는" | 생활 팁, 요리 |
| 뷰티/패션 | "뷰티 트렌드 관심" | 뷰티 퀴즈, 추천 |
| 투자 관심 | "금융 정보 관심" | 계산기, 세금 |
| 게임 이용자 | "게임 자주 하는" | 미니게임, 퀴즈 |

### 토스 유저 특성

- **핵심 활성층: 40대 이상** — 20대 CTR 매우 낮음
- 10대는 앱인토스 사용 불가

## 랜딩 URL

- 랜딩 URL은 정상 접속 가능한지 반드시 확인한다.
- **하나의 캠페인에서 소재별로 다른 랜딩 URL을 설정할 수 없다.** 캠페인 내 모든 소재는 동일한 랜딩 URL을 사용해야 한다.

## A/B 테스트 (보조 참고)

AI 자동 최적화가 기본이지만, 수동으로 문구 변수를 비교하는 A/B 테스트를 병행할 수 있다. 단, 발송 시간 설정은 AI 자동 최적화와 중복되므로 문구 변수 위주로 테스트한다.

### 테스트 변수 예시

| 변수 | A안 | B안 |
|------|-----|-----|
| 문구 스타일 | 정보형 "이번 주 소식" | 호기심형 "이거 받으셨나요?" |
| 이모지 | 없음 | 있음 |
| 수치 포함 | 없음 | "3개 남았어요." |

### 대조군 설정

- 변수 하나만 변경 (문구만)
- 최소 1일 이상 실행
