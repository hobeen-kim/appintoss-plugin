# 앱인토스 미니앱 무개입 생성 파이프라인

이 문서는 앱인토스 미니앱을 사람 개입 없이 생성·갱신하는 파이프라인의 **단일 출처(Single Source of Truth)** 다. `create`/`update` 커맨드와 모든 에이전트(planner, designer, reviewer, app-developer, back-developer, visual-qa)는 이 스킬에 정의된 페이즈·게이트·반려 규칙을 그대로 따른다. 이 명세에 없는 페이즈를 임의로 추가하지 않는다.

대상 범위: 미니앱 소스 생성 → 정적·비주얼 검증 → 빌드(`.ait`) → 검수 셀프체크 → 스토어 에셋 생성까지. **다크모드, 앱빌더(Deus) 자동화는 이 파이프라인의 범위가 아니다.** create/update 종료 시 `ait-console` 스킬로 콘솔 테스트 단계(앱 등록·에셋 업로드·테스트 버전 업로드·테스트 발송)까지 자동 수행한다. 검토 요청·출시는 사용자 명시 "출시해라" 명령에서만 — **파이프라인은 출시를 자동 수행하지 않는다.**

## 0. 증거 기반 원칙 (전 페이즈 공통)

**스크린샷 보고는 md 파일 임베드가 원칙.** 스크린샷·이미지를 보고할 때는 채팅에 경로를 나열하지 말고, 보고 md(`docs/REPORT-v*.md` 등)에 `![](상대경로)`로 **임베드**한 뒤 그 md 절대경로만 채팅에 제시한다(터미널은 이미지 인라인 불가). 보고 전 각 이미지를 Read로 확인한다.

증거 없는 PASS 금지, 조용한 폴백 금지. 모든 게이트 판정은 측정값(점수표·grep 결과·파일 경로·로그 원문)을 함께 기록한다. 게이트를 "적절히 판단"으로 통과시키지 않는다. 모든 게이트는 수치 또는 기계 판정 가능한 체크리스트로만 판정한다.

## 0-1. 하이브리드 문서 지침

번들 문서(이 플러그인의 `knowledge/`, `skills/*/references/`)는 stale일 수 있다. 불확실하면 공식 문서를 **우선** 조회하라. "공홈(공식 문서) 우선" 원칙은 유지하되, 조회 수단의 우선순위는 다음과 같다:

1. **ax MCP** (`apps-in-toss` 서버) — MCP가 연결된 세션이면 앱인토스 문서·코드 예제를 AI가 직접 참조할 수 있어 1순위. 또는 `docs-search` 스킬(`knowledge-skills@apps-in-toss-skills`).
2. **llms-full.txt** — 위 수단을 못 쓰면 다음 인덱스를 직접 조회:
   - https://developers-apps-in-toss.toss.im/llms.txt
   - https://developers-apps-in-toss.toss.im/llms-full.txt
   - https://tossmini-docs.toss.im/tds-mobile/llms-full.txt
3. **공홈 WebFetch** — https://developers-apps-in-toss.toss.im/ 직접 조회.

공홈과 번들 문서가 충돌하면 공홈을 신뢰하고, 발견한 드리프트를 생성 앱 `docs/DRIFT.md`에 구조화 집계한다(이후 `/appintoss:sync-docs`가 소비).

## 1. preflight (Phase 0 이전)

파이프라인 시작 전에 도구·환경을 점검한다. 누락 도구는 설치를 시도하고, 불가하면 시작 전 즉시 사람에게 보고한다.

| 점검 항목 | 기준 | 누락 시 |
|---|---|---|
| node | LTS 이상 | 설치 시도 → 불가 시 보고 |
| npm | 사용 가능 | 설치 시도 → 불가 시 보고 |
| Playwright | 설치 + chromium 브라우저 존재 (`npx playwright install chromium`) | 설치 시도 → 불가 시 보고 |
| 네트워크 | 공홈(https://developers-apps-in-toss.toss.im/) 도달 | 보고 후 번들 문서 폴백 모드로 진행 |
| ait/granite CLI | **프로젝트 로컬** `node_modules/.bin/ait`·`.bin/granite` (`@apps-in-toss/web-framework` 의존성). `npm install` 후 존재 확인 | 의존성 누락 시 install 재시도 → 불가 시 보고 |
| ax CLI + MCP | 권장(필수 아님) — `ax` 설치 + `apps-in-toss` MCP 등록 시 문서 참조 정확도 향상 | 미설치 시 brew 설치 시도 (`brew tap toss/tap && brew install ax` + `claude mcp add --transport stdio apps-in-toss ax mcp start`), 실패해도 파이프라인 진행 (llms.txt 폴백) |

ait/granite CLI는 전역 설치가 아니라 프로젝트 로컬이다. preflight 단계에서 `npm install`을 수행한 뒤 `node_modules/.bin/ait`가 존재하는지 확인한다. **빌드는 `npx ait build`** — 구 `granite build`는 웹 프로젝트에서 폐기되었다(실측 2026-06-07, 'no longer supported' 에러). dev 서버는 `granite dev` 또는 `vite`를 사용한다.

> **앱 사전 등록 권고**: 개발 착수 전 콘솔에서 앱을 미리 등록하면 심사 대기를 병렬화할 수 있다. 2026-05-14 등록 간소화로 이름·appName·유형만 입력하면 등록 가능 (출처: https://toss.im/apps-in-toss/blog/update-26-5-14 ). 필수 조건은 아니며 권고 사항이다.

## 2. create 모드 페이즈 정의 (Phase 0~7)

### Phase 0 — 기획 (토스 사용자층·행태 기반 브레인스토밍)

| 항목 | 내용 |
|---|---|
| 입력 | 사용자 주제 |
| 산출물 | `PLAN.md` (토스 적합 컨셉 + YAGNI 기능 정의 — 필요한 기능만, 추측성 기능 금지 + 수익 모델) |
| 담당 에이전트 | **planner ⇄ designer·reviewer (브레인스토밍 라운드)** |
| 정책 사전필터 | 금융상품 추천 금지 · 자사앱 설치 유도 금지 · 주요기능 외부의존 금지 · 연령등급 고려(만 14세+ 틴즈 노출 — 청소년 부적합 콘텐츠·과금 설계 점검) |
| 게이트 | `PLAN.md` 존재 + 정책 충돌 0건 + **designer·reviewer 컨셉 합의** + **수익 모델에 광고 필수 포함(최소 배너 배치 명시)** — 광고 미포함이면 게이트 보완 |

Phase 0은 planner가 주제를 토스 사용자층·행태에 맞춰 구체화하고, designer·reviewer가 코멘트로 검증하는 **브레인스토밍 라운드**로 진행한다. 서브에이전트끼리는 직접 통신할 수 없으므로, 라운드는 **오케스트레이터(커맨드 실행 주체)가 코멘트를 중계**한다(Phase 1의 designer⇄reviewer 크리틱 루프와 동일 패턴).

**브레인스토밍 라운드 규칙**:

1. **planner 컨셉 초안** — planner가 주제를 `knowledge/toss-user-insights.md`를 기반으로 구체화한다. 타겟 세그먼트, 토스 행태에 맞춘 기능 후보, 차별 컨셉 **2~3안**을 담은 컨셉 초안을 작성한다. PLAN.md에 핵심 전환 지표 1개 + 보조 지표 2개 포함(ait-analytics 스킬 기준).
2. **양측 코멘트** — 오케스트레이터가 초안을 designer·reviewer에 전달한다. designer는 UX 관점 코멘트(시그니처 모먼트 가능성, 화면 흐름 적합성), reviewer는 정책·검수 관점 코멘트(콘텐츠 제한·외부의존 리스크)를 각자 제시한다. 코멘트만 제시하며 컨셉 결정권은 planner에 있다.
3. **planner 수렴** — planner가 코멘트를 반영해 **1안으로 수렴**한다. designer·reviewer 양측이 명시적으로 동의하면 `PLAN.md`를 확정한다.
4. **최대 2라운드** — 1라운드에서 합의되지 않으면 코멘트를 반영해 2라운드를 진행한다. 2라운드에서도 미합의면 **planner 최종안으로 확정**하되, 미합의 쟁점을 `PLAN.md`에 기록한다.

정책 사전필터는 기능 정의 시점에 적용한다. 충돌 기능은 [에러 처리 표](#6-에러-처리-표)의 정책 충돌 규칙에 따라 제거·우회하거나, 주제 자체가 금지영역이면 즉시 중단한다.

### Phase 1 — 디자인

| 항목 | 내용 |
|---|---|
| 입력 | `PLAN.md` |
| 산출물 | `DESIGN.md` (페이지별 화면 구조 · TDS 컴포넌트 · 상태 · 플로우, **라이트모드 전용**) |
| 담당 에이전트 | designer ⇄ reviewer (크리틱 루프) |
| 게이트 | reviewer 크리틱 승인 — 체크리스트 전항목 충족 |

designer가 `DESIGN.md`를 작성하면 reviewer가 크리틱한다. 미충족 항목이 있으면 designer로 반려하여 재작업한다(크리틱 루프). 체크리스트 전항목 충족 시에만 게이트 통과.

### Phase 2 — 구현

| 항목 | 내용 |
|---|---|
| 입력 | `PLAN.md`, `DESIGN.md` (+ API 필요 주제는 `API.md`) |
| 산출물 | `src/` (미니앱 소스). API 필요 주제는 back-developer가 `API.md`를 **선행** 작성 |
| 담당 에이전트 | app-developer (+ back-developer) |
| 게이트 | `npx tsc -b --noEmit` 에러 0건 + lint 통과 |

API가 필요한 주제만 back-developer가 `API.md`를 먼저 작성하고, app-developer가 이를 참조해 `src/`를 구현한다. 게이트는 타입 체크 에러 0 + lint 통과.

**API 필요 주제**는 추가로 — 서버 빌드 성공 + 서버 기동 + `API.md` 명세 대비 엔드포인트 스모크(각 엔드포인트 1회 호출해 상태코드·스키마 확인) 통과. 프론트 게이트(tsc·lint)와 별개.

**스캐폴드 절차**: 신규 프로젝트는 공식 생성기 `npx create-ait-app {appName}`를 우선 사용한다(프롬프트에서 TDS 사용 **Y** 선택). 비대화형 환경이거나 생성기 실행이 실패하면 검증된 수동 스캐폴드(`package.json` / `vite` 설정 / `granite.config.ts`)로 폴백한다.

### Phase 3 — 비주얼 + 기능 동작 + 패널 합의 검증 루프

| 항목 | 내용 |
|---|---|
| 입력 | `src/`, `DESIGN.md` |
| 산출물 | (3-A) 화면별 스크린샷 + 100점 평가 점수표 · (3-B) `qa-flows.cjs` + 시나리오별 PASS/FAIL 결과 · (3-C) 3관점 PASS/CHANGES 판정 + 통합 위반 목록 |
| 담당 에이전트 | visual-qa (3-A·3-B·점수근거) + designer·reviewer (3-C 패널 관점, 오케스트레이터 중계) |
| 도구 | granite dev 서버 + Playwright (스크린샷·인터랙션, viewport **318×524 @2x**) |
| 게이트 | **3-A 85점 이상 AND 3-B 핵심 시나리오 100% 통과 AND a11y critical/serious 0건 AND 3-C 패널 합의 통과** |

Phase 3은 세 파트로 구성된다. 세 파트 모두 통과해야 게이트를 통과한다.

#### a11y 자동 스캔 (3-A/3-B/3-C와 병렬)

**a11y 자동 스캔** — Playwright + axe-core로 각 화면을 스캔하고, **critical/serious 위반 0건** 게이트를 적용한다. moderate 이하는 보고서에 기록한다.

**스캔 미실행 판정**: axe 설치·주입 실패로 스캔 자체가 미실행이면 **게이트 FAIL**이다. 단 **2회 재시도** 후에도 환경 원인(네트워크 등)으로 불가하면 **조건부 통과**로 처리할 수 있다 — 이 경우 `PIPELINE-LOG.md`·보고서에 `A11Y-SKIPPED` 플래그를 필수 기록하고, 환경 원인 증거(설치 로그)를 첨부해야만 유효하다. 플래그·증거 없는 스킵은 무효(FAIL)다.

#### Phase 3-A — 비주얼 평가 (정적 외관)

화면별 스크린샷을 캡처하고 100점 루브릭으로 채점한다.

평가 루브릭 (합계 100점):

| 항목 | 배점 |
|---|---|
| 레이아웃 정합 | 25 |
| TDS 일관성 | 25 |
| 터치 타겟·간격 | 20 |
| 타이포·컬러 위계 | 15 |
| 상태 완성도 (로딩·빈·에러 화면) | 10 |
| 개성·트렌디함 | 10 |

**개성·트렌디함 채점 기준**:
- 시그니처 모먼트 존재 (첫 화면에서 기억에 남는 1가지 — 큰 숫자 강조, 위트 있는 카피, 컬러 액센트 등): 없으면 -5
- 빈 상태·에러 화면이 기본 문구("데이터가 없습니다" 류)면 -3 (감정·위트 있는 카피여야 함)
- 전 화면이 동일 템플릿 반복으로 보이면 -2

주의: 이 항목도 TDS-only 제약 안에서 평가한다. 커스텀 컴포넌트 가점 금지 — 오히려 정적 검사(Phase 4) 위반이다.

3-A가 85점 미만이면 **점수표 + 위반 목록**과 함께 Phase 2로 반려한다.

#### Phase 3-B — 기능 동작 시나리오 (인터랙션)

정적 외관만으로는 실제 인터랙션 동작을 검증할 수 없으므로, `DESIGN.md`의 **"핵심 플로우 시나리오"** 를 Playwright 인터랙션 스크립트로 실행하여 실제 동작을 검증한다.

- **시나리오 출처**: `DESIGN.md`의 "핵심 플로우 시나리오" 섹션(designer가 Given/When/Then 형식으로 기술). visual-qa가 이를 Playwright 스크립트(`qa-flows.cjs`)로 변환·실행한다.
- **실행 방식**: dev 서버 위에서 클릭·입력·네비게이션을 수행한 뒤 화면 상태를 assertion한다 (예: "거래 추가 폼 제출 → 홈 목록에 새 항목 표시").
- **시나리오 수 기준**: 핵심 기능(PLAN.md **P0~P1**)당 최소 1개, **화면당 최소 1개 인터랙션**을 포함한다. `DESIGN.md`에 정의된 시나리오는 **전수 실행**한다(임의 생략 금지).
- **시나리오 전수 일치**: `DESIGN.md` '핵심 플로우 시나리오' 개수 N과 `qa-flows.cjs` 실행 시나리오 개수가 **일치해야 함**. `PIPELINE-LOG`에 `시나리오: 정의 N / 실행 M / 통과 K`를 기록하고 N≠M이면 게이트 실패(미구현 시나리오 보완).
- **모드별 시나리오 수 게이트 이원화**: **create 모드는 전수 일치(N=M)를 유지**한다. **update 모드는** Phase 0' 영향 분석에서 **영향받는 시나리오 부분집합 K개를 정의**하고, 그 K개의 정의·실행 개수가 일치하면 통과한다(`시나리오(update): 영향 정의 K / 실행 K' / 통과 P`, K≠K'이면 게이트 실패).
- **API 주제 실서버 호출**: API 주제의 3-B는 실제 기동된 로컬 서버에 호출(mock 아님), 서버 미가동 시 캡처 실패 처리.
- **게이트**: **핵심 시나리오 100% 통과**. 1건이라도 실패하면 **실패 시나리오명·기대값/실제값·에러 로그·실패 시점 스크린샷**과 함께 Phase 2로 반려한다.

#### Phase 3-C — 디자인 패널 합의 (스크린샷 다관점 검토)

3-A에서 visual-qa가 캡처한 **스크린샷을 3관점이 각각 검토·합의**한다. 비주얼 점수(3-A) 단독으로는 디자인 의도 부합·검수 규칙 위반을 충분히 잡지 못하므로, 동일한 스크린샷을 세 관점이 비판한다. 서브에이전트끼리는 직접 통신할 수 없으므로, **오케스트레이터가 visual-qa가 정리한 스크린샷 경로·화면명을 designer·reviewer에 전달**한다(Phase 1 designer⇄reviewer 크리틱 루프와 동일한 중계 패턴).

**3관점**:

- **designer 관점 (의도 부합)**: 구현 화면이 `DESIGN.md`의 디자인 컨셉·시그니처 모먼트·카피 보이스 의도대로 나왔는가. (코드 수정 없이 지적만)
- **reviewer 관점 (규칙 준수)**: 스크린샷에서 검수 UI 규칙·a11y·라이트모드·TDS 일관성 위반이 **육안으로** 보이는가. (Phase 4 정적 검사와 별개 — 이건 스크린샷 육안, Phase 4는 코드 grep)
- **visual-qa 관점 (객관 점수)**: 3-A 루브릭 점수의 근거.

**합의 규칙**: 3관점 각각 **PASS** 또는 **CHANGES(지적 목록)** 로 판정한다.

- 한 명이라도 **critical 지적**(검수 반려 사유급 위반 · 컨셉 정면 위배)을 내면 → **Phase 2로 반려**.
- critical이 없고 **minor 지적만** 있으면 → **과반(2/3) PASS면 통과**, minor 지적은 보고서에 기록한다.
- **전원 CHANGES면 당연히 반려**한다.

반려 시 3관점 지적을 통합한 위반 목록(**관점·항목·화면·measure**)을 Phase 2로 전달한다.

**오케스트레이터가 3관점 판정을 취합**해 합의 게이트(critical 1건→반려 / minor만→2/3 PASS 통과)를 적용한다. visual-qa는 자신의 점수만 제출하며 최종 판정자가 아니다.

#### Phase 3 게이트 종합

**3-A 85점 이상 AND 3-B 100% 통과 AND a11y critical/serious 0건 AND 3-C 패널 합의 통과**일 때만 Phase 3 게이트를 통과한다. 어느 하나라도 미달이면 해당 증거(3-A 점수표·위반 목록 / 3-B 실패 시나리오·에러 로그 / a11y 위반 집계 / 3-C 3관점 통합 위반 목록)와 함께 Phase 2로 반려한다.

**외부 링크 인지 UI 체크**: `openURL` 등 외부 이동 호출 지점마다, 이동 **전에** 사용자가 외부로 나간다는 것을 인지할 수 있는 UI(모달 확인 또는 명시적 라벨)가 있는지 확인한다. 누락 시 게이트 FAIL. 자동 검수(네뷸라)가 정상 구현을 오탐하는 경우가 있으며, 이때는 채널톡으로 수동 승인을 요청하는 경로가 존재한다 (실사례: https://techchat-apps-in-toss.toss.im/t/pokit-6/3883) — 오탐 대응 안내를 보고서에 기록한다.

| 항목 | 내용 |
|---|---|
| 입력 | `.ait`, `src/`, 전 페이즈 산출물 |

검수 11단계 체크리스트와 알려진 반려사례를 대조하여 각 항목에 증거(파일 경로·grep 결과·로그·스크린샷)를 첨부한다. FAIL 항목은 **원인 페이즈로 반려**한다(예: UI 위반은 Phase 2, 디자인 누락은 Phase 1).

검수 통과 후 `ait-submit` 스킬로 `docs/APP-SPEC.md`(앱 전체 명세 마스터)와 `docs/SUBMIT.md`(콘솔 제출 최소 문서)를 생성·갱신한다. APP-SPEC.md에 전체 명세 — 앱 기본 정보·수익 모델·기술 스택·스토어 노출 정보(부제·상세 설명·카테고리·검색 키워드)·**제출 에셋 임베드**(`docs/assets/`의 아이콘·화면예시 3·썸네일을 상대경로+미리보기로 기록)·출시노트(앱 소개 3~6줄, 최초 1회)·**업데이트 노트(버전별 누적, update마다 최신 버전을 맨 위에 추가·기존 보존)**·앱 내 기능(전체)·광고 노출 트리거 명세·푸시 상세·토스 로그인 설정·검수 안내·자가점검·업로드 절차 — 를 모두 채운다. 그중 **출시/업데이트 노트와 앱 내 기능(최대 3개 딥링크) 두 섹션만** SUBMIT.md에 추린다.

**2-문서 모델**: `docs/APP-SPEC.md`는 앱 전체 정보를 담는 superset 마스터 — 에셋·스토어 노출 정보·토스 로그인 설정·검수 안내·자가점검·업로드 절차·수익 모델·기술 스택·광고 노출 트리거 명세·푸시 상세·기능 동작 상세(전체 화면) 등을 모두 포함한다. `docs/SUBMIT.md`는 출시/업데이트 노트 + 앱 내 기능만 담는 **최소 콘솔 문서**다. 두 문서가 충돌하면 APP-SPEC.md가 우선한다. 필수 항목은 ait-submit 스킬 "2-문서 규칙"을 따른다.

### Phase 8 — 완료 보고·승인 게이트 (create 모드)

| 항목 | 내용 |
|---|---|
| 입력 | 전 페이즈 산출물 (`PIPELINE-LOG.md`, `REVIEW-REPORT.md`, `docs/APP-SPEC.md`, `docs/SUBMIT.md`, `qa-screens/`, `docs/assets/`) |
| 산출물 | `docs/REPORT-v{version}.md` (양식은 `skills/pipeline/references/report-template.md` 준수) |
| 담당 에이전트 | visual-qa (스크린샷 보유 주체) |
| 게이트 | 보고서 존재 + 필수 섹션 전부 채움 + **승인 게이트 통과** (모드에 따라 수동 승인 대기 또는 자동 승인 후 Phase 9 진행) |

파이프라인이 끝나면 **사람이 읽고 허가할 보고 파일**을 생성한다. 보고서에는 변경 내역과 스크린샷이 임베드되어, 사용자가 파일 하나만 보고 승인 여부를 결정할 수 있어야 한다. 측정값은 `PIPELINE-LOG.md`·`REVIEW-REPORT.md`에서 **전재**한다(재측정 금지, 증거 재사용). 스크린샷은 보고서 기준 **상대경로**로 임베드한다.

**승인 게이트 모드 — 2가지**:

**모드 결정**: 명령행 `--auto` > `.appintoss.json` autoMode > 기본 수동.

- **수동 승인(기본)**: 기존대로 보고서 생성 후 **사용자 승인 대기로 종료**(파이프라인이 자동으로 더 진행하지 않음 — 승인은 사람의 유일한 개입 지점). 오케스트레이터는 보고서 경로를 제시하고 멈춘다. 사용자가 승인하면 콘솔 업로드(수동) 또는 직접 커밋, 수정 요청이면 해당 페이즈로 반려한다. **수동 모드는 Phase 8에서 종료한다(Phase 9 미실행).**
- **자동 모드(`--auto`)**: 보고서 생성 후 **승인을 기다리지 않고 자동 승인 처리하여 다음 단계(Phase 9 git 자동 푸시)로 진행**한다. 보고서는 사후 확인용으로 남긴다.

**자동 모드 무조건 중단·보고 예외**(아래 중 하나라도 해당하면 자동 진행 금지, 사람에게 보고 후 종료):
1. 정책 금지영역 주제 (금융상품 추천 등 — Phase 0 중단 예외와 동일)
2. 동일 페이즈 반려 5회 초과 (§4 반려 한도 도달)
3. 빌드 실패 (Phase 5 게이트 미통과)

위 예외에서는 자동 모드라도 Phase 9로 진행하지 않고 현재 산출물 + 사유를 보고한다.

**실행 경험 저장(Honcho)**: 실행 중 발견한 공홈 문서 드리프트, 반복된 반려 패턴, 트러블슈팅 교훈은 Honcho 메모리에 conclusion으로 저장한다 (`mcp__plugin_honcho_honcho__create_conclusion`, observer_id: claude, observed_id: hobeen — 1~2문장, 다음 실행의 정확도 향상 목적). Honcho 도구가 없는 세션에서는 생략하고 보고서 §7에 기록만 남긴다.

### Phase C — 콘솔 테스트 (create 모드, Phase 8 직후 자동 수행)

| 항목 | 내용 |
|---|---|
| 입력 | `.ait` 번들, `docs/assets/`, `docs/SUBMIT.md` |
| 산출물 | 콘솔 등록·에셋·테스트 버전·테스트 발송 완료 상태, 각 단계 결과를 보고서에 기록 |
| 담당 스킬 | `ait-console` |
| 게이트 | `test-send` 성공(단말 푸시 발송 요청 완료) |

Phase 8 보고서 생성 직후 `ait-console` 스킬을 통해 콘솔 테스트 단계를 자동 수행한다:

1. **register** — 동일 appName이 콘솔에 없으면 앱 등록(이름·appName·유형)
2. **upload-assets** — `docs/assets/` 아이콘·화면예시·썸네일 업로드
3. **upload** — 번들을 테스트 버전으로 업로드
4. **test-send** — 테스트 발송("푸시 보내기") 실행

각 단계의 성공·실패 결과는 `docs/REPORT-v{version}.md`의 §콘솔 테스트 단계에 기록한다. 단계 실패 시 실패 단계명·스크린샷 경로를 보고서에 남기고 계속 진행하지 않는다.

**Phase C는 테스트 발송까지만 자동이다 — test-send는 upload 성공 시 무조건 수행(실앱 포함, 보류 금지). 검토 요청·출시는 자동 수행하지 않는다.**

### Phase C' — 콘솔 테스트 (update 모드, Phase 8' 직후 자동 수행)

Phase C와 동일하되 register·upload-assets를 생략하고 upload(테스트 버전) → test-send만 수행한다. **test-send는 upload 성공 시 무조건 수행한다 — 실앱 포함, 보류 금지.** 결과는 update 보고서에 기록한다.

---

### 출시 상태머신·비동기 watcher (별도 명령 — 파이프라인 자동 단계 아님)

아래 단계는 파이프라인이 자동 호출하지 않는다. 사용자가 "출시해라"라고 명시 명령할 때만 개시한다:

| 명령 | 설명 |
|---|---|
| `ait-console submit-review` | 검토 요청 버튼 클릭 + SUBMIT.md 출시/업데이트 노트 전재 |
| `ait-console release-watch` | 심사 APPROVED 폴링 → 활성 시 release 실행 (1시간 간격 크론) |
| `ait-console ad-apply` | 광고 unit ID 신청 |
| `ait-console ad-id-watch` | 광고 ID 발급 감지 → config 스왑·재빌드·테스트 재배포 |
| `ait-console template-watch` | 기능성 템플릿 심사 통과 감지 → 발송 활성화 알림 |

**자동 출시 금지 — release·release-watch는 사용자 명시 명령 개시 체인에서만 실행한다.**

### Phase 9 — git 자동 푸시 (자동 모드 한정, 신규)

| 항목 | 내용 |
|---|---|
| 입력 | 전 페이즈 산출물 (소스 + 보고서 + `docs/APP-SPEC.md` + 에셋), `.appintoss.json`(있으면) |
| 산출물 | 로컬 커밋(+ remote 있으면 push), 결과를 `docs/REPORT-v{version}.md`에 기록 |
| 담당 에이전트 | reviewer |
| 게이트 | 커밋 생성됨 + (remote 있으면 push 성공 / 없으면 "remote 미설정 — 로컬 커밋만" 기록 후 정상 종료) |

**자동 모드에서만, Phase 8 자동 승인 후** 실행한다. **수동 모드는 Phase 8에서 종료**하므로 Phase 9를 실행하지 않는다(사람이 직접 커밋).

**절차**:
1. git 저장소가 아니면 `git init`.
2. 변경 파일 `git add` (의도한 산출물만 — `.gitignore` 준수).
3. 커밋. 메시지: `feat(appintoss): {앱명} v{version} - {1줄 요약}`, 끝에 다음 trailer 추가:
   ```
   Co-Authored-By: Claude <noreply@anthropic.com>
   ```
4. remote가 있으면 **현재 브랜치**를 push. remote가 없으면 `docs/REPORT-v{version}.md`에 "remote 미설정 — 로컬 커밋만" 기록 후 정상 종료.

**가드(파괴적 작업 금지)**:
- force push 금지(`--force`/`-f` 금지), history rewrite 금지(`rebase`/`reset --hard`/`commit --amend` 금지).
- 기본 브랜치가 `main`이고 remote가 공유 저장소면, main 직접 push 대신 별도 브랜치 사용을 권장한다(보고서에 1줄 안내).
- `.appintoss.json`의 `git.branch` 설정이 있으면 그 브랜치를 사용한다.

**결과 기록**: 커밋 해시·브랜치·push 여부를 `docs/REPORT-v{version}.md`의 §빌드 또는 새 §배포 줄에 추가한다.

### Phase 8' — before/after 비교 보고 (update 모드 마지막 페이즈)

Phase 8과 동일하되, 변경 화면의 **before/after 스크린샷을 나란히 비교**(Before·After 표)하는 것을 필수로 포함한다. before는 Phase 0'에서 `qa-screens/before/`에 캡처한 기준 스크린샷을, after는 Phase 3' 변경 화면 캡처를 사용한다. before가 없으면("before 없음" 사유 기록된 경우) after만 임베드하고 사유를 명시한다.

또한 update 모드 보고서에는 **§3-1 업데이트 노트**(report-template 양식)를 필수로 작성한다 — 이번 버전에서 무엇이 달라졌는지 사용자 관점 1~3줄 + 버전 변화. 이 내용은 `docs/SUBMIT.md`의 출시노트(재제출용)와 동일하게 반영한다.

## 3. update 모드 페이즈 정의 (Phase 0'~7')

기존 미니앱을 갱신할 때 사용한다. Phase 2~6은 create 모드와 동일하며, 비주얼 검증(Phase 3)은 **변경된 화면만** 캡처한다.

### Phase 0' — 영향 분석

| 항목 | 내용 |
|---|---|
| 입력 | 기존 `PLAN.md` · `DESIGN.md` · `API.md`, 변경 요구 |
| 산출물 | 변경 범위 · 영향 화면 식별 결과 + **변경 전(before) 영향 화면 스크린샷** (`qa-screens/before/`) |
| 담당 에이전트 | planner (before 캡처는 visual-qa에 위임) |

기존 스펙 문서를 로드해 변경 범위와 영향받는 화면을 식별한다. 스펙이 없는 외부 프로젝트면 **코드 역분석으로 스펙을 복원**한 뒤 진행한다.

**before 캡처**: 영향 분석으로 식별된 영향 화면을 변경 적용 **전에** 캡처한다(dev 서버 + Playwright, viewport **318×524 @2x**, `qa-screens/before/`에 저장). Phase 8' before/after 비교의 기준이 된다. 캡처는 visual-qa에 위임한다. 빌드가 깨진 상태 등으로 캡처가 불가하면 "before 없음" 사유를 기록한다.

### Phase 1' — 스펙 갱신

| 항목 | 내용 |
|---|---|
| 입력 | Phase 0' 영향 분석 결과 |
| 산출물 | `DESIGN.md` 증분 수정 (영향 페이지만) |
| 담당 에이전트 | designer |
| 게이트 | reviewer 크리틱 승인 |

`DESIGN.md`에서 영향받는 페이지만 증분 수정하고 크리틱한다.

### Phase 2'~6' — create와 동일

Phase 2(구현) ~ Phase 6(검수 셀프체크)은 create 모드와 게이트·담당이 동일하다. 단, Phase 3 비주얼 검증은 **변경된 화면만** 캡처·평가한다.

**Phase 3'은 변경 화면만 대상으로 3-A/3-B/3-C를 동일 수행**한다. 3-B 시나리오 수 게이트는 모드별로 이원화한다 — create는 전수 일치(N=M) 유지, update는 Phase 0' 영향 분석에서 정의한 **영향 시나리오 부분집합 K개**의 정의·실행 일치로 판정한다. 추가로 **update 회귀 스모크**를 수행한다: 변경과 무관한 핵심 시나리오 1개를 재실행한다. 실패가 이번 변경이 원인이면 Phase 2로 반려하고, 기존 결함(변경 전부터 존재)이면 보고서에 기록 후 진행한다. 3-C 패널은 변경 화면의 **before/after 스크린샷을 비교 검토**한다 — designer 관점은 개선 의도대로 바뀌었는지, reviewer 관점은 변경으로 인한 회귀(검수 규칙·a11y·라이트모드·TDS 위반 신규 발생)가 없는지 본다. before는 Phase 0'에서 `qa-screens/before/`에 캡처한 기준 스크린샷, after는 Phase 3' 변경 화면 캡처를 사용한다(before 없으면 after만 검토하고 사유 기록). 합의 규칙·게이트는 create 3-C와 동일하다.

### Phase 7' — 에셋 갱신 (조건부)

변경된 화면이 기존 화면예시 3장에 포함될 때만 해당 화면예시를 재캡처한다. 변경이 화면예시에 영향을 주지 않으면 에셋 갱신을 생략한다.

### Phase 8' — 완료 보고·승인 게이트

create 모드 Phase 8과 동일한 승인 게이트(수동 승인 기본 / `--auto` 자동 모드)를 적용한다. `docs/REPORT-v{version}.md`를 생성하고, update 모드는 §2의 Phase 8' 정의(before/after 비교 필수)를 따른다. 자동 모드면 Phase 8 자동 승인 후 **Phase 9 git 자동 푸시**로 진행한다(수동 모드는 여기서 종료). 자동 모드 무조건 중단·보고 예외(정책 금지영역 · 반려 5회 초과 · 빌드 실패)는 create와 동일하다.

## 4. 반려 규칙

**반려 = 게이트 미통과 산출물을 구체적 위반 목록과 함께 원인 페이즈 담당 에이전트로 되돌려 재작업시키는 자체진단 루프. 사람 개입 아님.**

- **동일 페이즈 반려 한도 5회** — 초과 시 파이프라인을 중단하고, 현재 산출물 + 미해결 위반 목록을 사람에게 보고한다.
- 반려 시 반드시 포함:
  1. 위반 항목 목록 — 파일:라인 또는 화면명
  2. 게이트 기준 대비 측정값 (예: "비주얼 78/85점", "비TDS import 3건")
  3. 이전 시도에서 금지할 접근 — 같은 실패를 반복하지 않도록 명시

**반려 후 재진입 시 재수행 후속 페이즈 범위** — 후행 페이즈(예: Phase 6) FAIL로 선행 페이즈(예: Phase 2)로 반려해 재작업한 경우, 그 사이 페이즈를 전부 무조건 재수행하지 않는다:

- **변경 영향 페이즈는 재수행** — 재작업으로 산출물·코드가 바뀌어 기존 게이트 증거가 무효화된 페이즈는 다시 실행한다. 예: Phase 6 FAIL→Phase 2 반려로 `src/`가 수정되면 Phase 3(비주얼·동작 — update 모드의 "변경 화면만" 규칙 준용 가능)·Phase 4(정적 검사)·Phase 5(빌드 — 소스가 바뀌었으므로 항상 재수행)를 재수행한 뒤 Phase 6으로 복귀한다.
- **변경 무관 페이즈는 기존 증거 유지** — 재작업 범위와 무관한 페이즈의 기존 PASS 증거는 유효하다. 예: Phase 2 재작업이 디자인 스펙을 건드리지 않으면 Phase 1은 재수행하지 않는다.
- 재수행·유지 판단 근거(어떤 페이즈를 왜 건너뛰었는지)를 `PIPELINE-LOG.md`에 1줄씩 기록한다.

## 5. 재개 규칙

중단·실패로 끊긴 파이프라인을 처음부터 다시 돌리지 않고, 마지막으로 통과한 페이즈 다음부터 재개한다.

### PIPELINE-LOG.md 기록 형식 (표준)

각 페이즈 게이트 판정은 기계 파싱 가능하도록 다음 형식으로 `PIPELINE-LOG.md`에 기록한다.

```
## Phase {N} — {이름}
판정: PASS|FAIL ({측정값 요약})
```

- `## Phase {N} — {이름}` 헤더 1줄 + `판정: PASS|FAIL ({측정값 요약})` 1줄을 페이즈마다 남긴다.
- 측정값 요약 예: `판정: PASS (비주얼 88점, 동작 4/4 통과)`, `판정: FAIL (비주얼 78점)`.
- update 모드는 로그 상단에 처리한 **변경 요청 문자열**을 기록한다 (예: `변경 요청: 월별 통계 화면 추가`).
- **반려 누적 섹션** — 로그 하단에 페이즈별 반려 횟수·사유를 누적 기록한다. 반려가 발생할 때마다 갱신하며, §4 반려 한도(동일 페이즈 5회) 판정의 단일 출처다.

```
## 반려 누적
반려 누적: Phase 3: 2회 (사유: 시나리오 N≠M)
반려 누적: Phase 2: 1회 (사유: 비TDS import 3건)
```

### 재개 판정 절차

create/update 시작 시 대상 디렉토리에 `PIPELINE-LOG.md`가 있으면:

1. 로그에서 **마지막 `판정: PASS` 페이즈**를 찾는다.
2. 그 페이즈의 산출물 파일이 **실재하는지 교차 확인**한다 (예: Phase 1 PASS면 `DESIGN.md`, Phase 5 PASS면 `*.ait` 존재 확인).
3. 두 조건(로그의 마지막 PASS + 산출물 실재)을 **둘 다 충족하면 다음 페이즈부터 재개**한다. 사용자에게 "Phase N부터 재개" 1줄 보고 후 무개입 진행한다.
4. 산출물 누락·로그 불일치(로그는 PASS인데 산출물 없음)면 **해당 페이즈부터 다시** 실행한다.
5. 반려 카운트는 `PIPELINE-LOG.md`의 반려 누적 섹션에서 복원하며, 세션 재개 시 리셋을 금지한다.

### 재개 차단 예외

- 사용자가 **"처음부터"** 라고 명시하면 로그를 무시하고 전체 재실행한다.
- **update 모드**는 로그에 기록된 변경 요청 문자열과 이번 변경 요청이 **다르면 재개 불가** — 새 실행으로 처음부터 진행한다 (같은 변경 요청일 때만 재개).

## 6. 에러 처리 표

자동 복구는 **진단 → 1~3회 재시도 → 중단**으로 통일한다.

| 실패 | 처리 |
|---|---|
| 정책 충돌 주제 | 충돌 기능만 자동 제거·우회. 주제 자체가 금지영역이면 즉시 중단 + 대안 제시 (유일한 시작 차단 예외) |
| granite dev/build 실패 | `ait-build` troubleshooting 자가진단 → 공홈 재조회(버전 드리프트 의심) → 에러 로그 원문과 함께 보고 |
| SDK/TDS API 불일치 (번들 문서 stale) | 해당 API만 공홈(https://developers-apps-in-toss.toss.im/) 재조회 후 재시도. 해결 시 드리프트를 생성 앱 `docs/DRIFT.md`에 구조화 집계(이후 `/appintoss:sync-docs`가 소비) |
| 공홈 조회 실패 | 번들 문서 폴백 + `REVIEW-REPORT.md`에 "공홈 미검증" 명시 |
| 번들 100MB 초과 | 에셋 최적화 1회 자동 시도 → 실패 시 크기 내역과 함께 보고 |
| 스크린샷 캡처 실패 | dev 서버 로그 확인 → 포트 충돌 재시도 → 렌더 실패는 Phase 2 반려로 전환 |

## 7. 페이즈 흐름 요약
