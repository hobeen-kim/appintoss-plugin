# 출시 후 성장 플레이북 (실측 사례 기반)

> 출처: 앱인토스 공식 웨비나 2026-08-21 「혼자 만든 미니앱으로 하루 150만원 매출까지」
> — 박효준(토스 iOS 개발자), 대표작 「인스타 언팔한 사람 찾기」 · 미니앱 8개 운영
> 원문 정리: `docs/webinar-2026-08-21/` (전문·요약·발표자료)
>
> **일반화 주의**: 아래 수치는 특정 미니앱(인스타 연동 · 10·20대 · 990원 단건 결제 + 광고)의 실측치다.
> 절대 기준이 아니라 **"이 정도 범위가 나온다"는 참고선**과 **의사결정 절차**로 사용한다.

## 0. 전제 — 출시는 끝이 아니라 시작이다

제로 → 원 흐름에서 **앱 출시까지는 AI가 거의 다 해준다.** 실제 성과를 가르는 구간은 그 뒤다.

```
① MCP 세팅 → ② 기획(PRD) → ③ 디자인 → ④ 개발 → ⑤ 출시     ← AI 위임 가능
                                    ⑥ 홍보·마케팅 ⇄ ⑦ 유지보수  ← 사람이 계속 반복
```

가장 흔한 실패 패턴: **출시 후 "반응이 없네" 하고 그만두는 것.**
실제 사례에서는 출시 후에도 **약 200회(콘솔 빌드 내역 20행 × 10페이지)** 를 고쳤다. 문구 하나까지
직접 단말로 플로우를 타보며 "이 문구가 직관적인가 / 다음 화면으로 갈 수 있게 안내하고 있나"를 점검했다.

**성장 루프 (이 문서의 뼈대)**

```
로그를 심는다 → 대시보드로 퍼널을 본다 → 최대 이탈 구간을 찾는다
   → 그 지점에만 손을 댄다 → 지표로 효과를 검증한다 → 반복
```

## 1. 노출을 만드는 3계층

| 계층 | 수단 | 비용 | 우선순위 |
|---|---|---|---|
| ① **플랫폼 제공** | 스마트 발송(광고성·기능성), 프로모션, 공유 리워드, 리뷰 요청, 공유 링크 이미지 | 대부분 무료 | **집중** |
| ② **외부 채널** | 인스타 · 스레드 · 틱톡 · X · 에브리타임 등 | 시간 | **집중** |
| ③ **플랫폼의 노출 확대** | 앱인토스가 성과 좋은 앱을 더 노출 | — | 기대 대상 아님(①②의 결과) |

**선순환**: ①②로 성과를 낸다 → 플랫폼이 "사용자 가치가 있는 앱"으로 판단 → ③ 노출 확대 → 재성장.

### 실측 성장 곡선

| 시기 | 상태 | 원인 |
|---|---|---|
| 출시 ~ 15일 | 반응 거의 없음 (DAU 10명대) | 유입이 전부 지인. 지인 피드백으로 개선 |
| 그 후 | **500명씩 스파이크** | **스마트 발송(광고성)** 첫 사용 |
| 반복 | 평균 유입 계단식 상승 | 스파이크를 반복해 기준선 자체를 올림 |
| 출시 약 1개월 | **누적 147만 명** | 유입 → 정착 → 활성화 선순환 |

> 첫 목표를 **DAU 10명**으로 잡은 이유: 일반 앱스토어·플레이스토어는 **하루 1명 유입도 극히 어렵다**
> (스토어가 홍보해주지 않으므로 바이럴·지인·유료 마케팅이 없으면 유입이 0에 수렴).
> 앱인토스는 이보다 훨씬 용이하다는 점이 미니앱을 선택하는 실질적 이유다.

## 2. 플랫폼 채널 — 무엇을 언제 쓰는가

| 채널 | 핵심 가치 | 실측 성과 | 상세 문서 |
|---|---|---|---|
| **스마트 발송(광고성)** | **내 앱을 한 번도 쓴 적 없는 유저에게 도달**하는 유일한 무료 수단 | 클릭 500회 사례 → "이것만 잘 써도 1,000명은 유입 가능" | `ait-smart-message` |
| **스마트 발송(기능성)** | 앱 내 이벤트 기반 알림. 동의·행동 기반이라 CTR이 광고성보다 높음 | 이탈 복귀 **40%**, 주간 리텐션 알림 CTR **60%** | `ait-smart-message` |
| **프로모션(토스 포인트)** | 포인트를 주며 홍보. **토스 두 번째 「혜택」 탭에 노출** | — | `ait-promotion-reward` |
| **공유 리워드(contactsViral)** | 유저가 지인에게 토스 푸시 발송. **공유 여부를 앱이 감지 가능** → 보상 설계 | — | `ait-sdk/references/ait-contacts-viral.md` |
| **공유 링크 이미지 커스텀** | 링크 메타데이터 이미지를 바꿔 카톡 공유 시 가치가 드러나게 | — | `ait-sdk/references/ait-share.md` |
| **리뷰 요청(requestReview)** | 화면 이탈 없이 별점 입력 | 리뷰 **7,000개 · 평점 4.5+** (초기엔 100개 미만·낮은 평점) | `ait-sdk/references/ait-interaction.md` |

### 대부분이 여기서 멈춘다

- 많이 쓰는 것: 스마트 발송, 프로모션
- **모르거나 "엄두가 안 나서" 안 하는 것: 공유 리워드 · 공유 링크 이미지 커스텀 · 리뷰 요청 · 외부 채널**

→ 미니앱 마케팅 점검 시 **후자 4개가 비어 있는지 먼저 확인한다.** 마케터가 아닌 개발자도 전부 수행 가능한 범위다.

## 3. 외부 채널 마케팅

- **계정 1개 + 링크트리**: 앱이 여러 개면 SNS 계정 하나를 운영하고 링크트리로 전 앱 링크를 모은다(유저 집결점).
- **콘텐츠는 가볍게**: CapCut 등으로 게시물·릴스를 간단히 제작. *"잘 만들어야지" 하며 실행을 늦추지 않는다.*
- **채널**: 스레드 · 인스타그램 · 틱톡 · **X(트위터)** · **에브리타임** 등.
- **데이터로 채널을 고른다**: 콘솔 대시보드 **연령 분포**를 보고 그 층이 모인 커뮤니티를 공략한다.
  (실측 사례: 10·20대가 가장 두꺼움 → 에브리타임 집중)
- **바이럴은 통제할 수 없지만 대비할 수 있다**: 제3자가 올린 X 게시물이 **조회수 360만** → 다음 날 **검색 유입 약 2만 명**.
  이런 스파이크가 2~3회 발생. **초반 화력을 높이면 유저가 관심을 가져준다.**

## 4. 이탈 진단 → 개선 (핵심 사례)

### 4.1 로그가 없으면 아무것도 못 한다

- 로그 = **유저가 앱에서 돌아다닌 흔적**(클릭 · 화면 조회 · 체류 등). 정의하기 나름이다.
- **유저는 "나 이제 종료해요"라고 말해주지 않는다.** 이동·클릭·노출을 직접 정의해 심어야 지표가 생긴다.
- AI에게 개발을 시킬 때 **"다른 건 몰라도 로그는 반드시 함께 작성하라"** 고 명시한다.

### 4.2 진단 — 무엇이 문제였나

퍼널상 **4단계 → 5단계**에서 이탈이 가장 컸다. 로그로 밝혀낸 원인:

1. 토스 앱 → 인스타그램 앱으로 이동해야 함
2. 데이터 요청 후 **응답까지 10~15분**
3. 대기 중 유저가 잊어버림
4. 메일을 받아도 **알림이 없어 또 잊음**
5. → 돌아오지 않음

### 4.3 처방 — 기능성 푸시 한 방

**"15분 뒤에 알림을 보내 드릴게요, 받으시겠습니까?"** 동의를 받고 이메일 도착 시점에 맞춰 발송.

| 지표 | 값 |
|---|---|
| 발송 | 3만 명 |
| 복귀 | 1만 명 이상 |
| **복귀율** | **약 40%** ("푸시로 40%면 매우 높다") |
| 해당 구간 전환 | **+14%p** |
| 최종 전환 | **9% → 14% (+5%p)** |

> 앞 구간은 손대지 않아 **전후 수치가 동일** → 푸시의 순효과임이 지표로 증명됐다.
> **대시보드가 먼저 있었기 때문에** "무엇을 고칠지"를 추측하지 않아도 됐다.

### 4.4 이 개선이 매출이 되는 이유

**결과 화면을 본 유저의 23%가 결제까지 전환**한다. 따라서 논리는 단순하다.

```
이탈을 줄인다 → 결과 화면 도달 증가 → 23% 전환 적용 → 매출 증가
```

**퍼널 개선은 곧 수익화 작업이다.** 결제 UI를 손대기 전에 이탈부터 본다.

## 5. 리텐션 — 다시 올 이유 만들기

단건 결제형 앱은 "한 번 쓰고 끝"이 되기 쉽다. 사례에서 쓴 3가지:

| 수단 | 설계 | 실측 |
|---|---|---|
| **주기적 기능성 알림** | "이번 주 팔로우 변화를 보실래요?" — 유저가 여유로운 **토요일 오전** 등 타이밍을 노려 발송 | 5만 발송 → 3만 클릭, **CTR 약 60%** |
| **기능 개선** | 리뷰에서 반복된 요구(과거 이력 · 기간별 변화 · 새 팔로워)를 반영해 **계속 쓸 이유**를 만듦 | — |
| **리뷰 관리** | 유저가 만족한 순간에 `requestReview` 호출 | 리뷰 7,000개 · 4.5+ |

> **알림의 발송 시점(요일·시간대)까지 설계 대상**이다. 문구만 다듬고 시점을 방치하면 CTR이 나오지 않는다.

## 6. 운영 자동화 — 여러 앱을 동시에 굴리는 법

### 6.1 문의 응대 자동화

앱이 터졌을 때 **시간당 약 50건**의 문의가 들어왔다. 견디며 응대하다 발견한 것:
**문의도 비슷하고 내 답변도 똑같다** → 자동화 대상.

구축 방식(사례):
1. 집의 안 쓰는 컴퓨터를 상시 켜둔다
2. 로컬에 **무료 AI**를 계속 띄워둔다 (유료 코딩 도구가 아니어도 된다)
3. 문의가 들어오면 **유형을 판별해 답변 초안을 작성**
4. 사람은 **보내기 버튼만** 누른다

### 6.2 다앱 운영 3원칙

| # | 원칙 | 이유 |
|---|---|---|
| 1 | **공통 지식은 한 곳에서 관리** | 앱인토스 개발 내용은 결국 비슷하다. 지식이 한 곳에 있으면 따로 지시하지 않아도 AI가 방향을 잡는다 |
| 2 | **PRD로 개발 범위를 잠근다** | AI는 시키지 않은 것도 만든다. 범위를 문서로 고정해야 의도한 것만 나온다 |
| 3 | **운영은 자동화, 지표는 필수** | 대시보드가 없으면 전환율·클릭률을 볼 수 없고, 개선 판단이 감(感)이 된다 |

## 7. 점검 체크리스트

**출시 직후**
- [ ] 스마트 발송(광고성)으로 첫 신규 유입 만들기 — 미사용 유저 도달은 이 채널뿐
- [ ] 공유 링크 미리보기 이미지 커스텀
- [ ] `requestReview`를 "유저가 만족한 순간"에 호출
- [ ] 지인 배포 → 초기 피드백 수집

**성장 단계**
- [ ] 대시보드에서 **최대 이탈 구간** 특정 (로그가 없으면 여기서 막힌다)
- [ ] 그 구간에 **기능성 푸시** 투입 (동의 기반)
- [ ] **재방문 알림** 설계 — 문구 + **요일·시간대**
- [ ] 프로모션 + 공유 리워드 도입
- [ ] 대시보드 **연령 분포** → 해당 층이 모인 외부 커뮤니티 공략
- [ ] 광고 유형 실험(전면형 ↔ 리워드) → `ait-sdk/references/ait-ads.md`
- [ ] 결제 선택지 다양화 + 부분 공개 → `ait-sdk/references/ait-iap.md`
- [ ] 문의가 늘면 응대 자동화

## 8. 관통 원칙

> **"엄청나게 갖춰서 출시하려 할 필요 없다.
> 문제 정의를 빠르게, 개발도 빠르게, 마케팅도 해보고,
> 반응이 좋으면 계속하고 아니면 다른 걸로 다시 도전한다."**

1. **작게 시작한다** — 화면 1~2개, DAU 10명부터
2. **빈칸을 찾는다** — 오리지널이 아니어도 된다. 생태계에 없으면 그게 기회다
3. **제약을 설계로 바꾼다** — 서버를 못 만들면 서버 없는 앱을 만든다
4. **출시는 시작이다** — 고치고, 로그를 심고, 지표로 페인 포인트를 찾는다
5. **플랫폼의 무료 도구를 끝까지 쓴다**
