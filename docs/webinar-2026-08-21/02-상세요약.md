## 1부. 기획 — "빈칸을 찾고, 제약을 무기로"

### 1.1 시작 계기와 첫 목표

- **유저로 먼저 접함.** 토스 안의 게임들을 하다가 "이런 게 앱인토스구나, 미니앱이구나"를 알게 됨.
- 매력 포인트는 **"토스라는 큰 생태계 안에 내 앱을 넣을 수 있다"**는 것. 실제로 해보니 어렵지도 않고 누구나 출시 가능한 구조였음.
- 첫 목표는 거창하지 않게 **DAU 10명**.

> **왜 DAU 10명이 의미 있는 목표인가 (일반 스토어와의 대비)**
> - 앱스토어·플레이스토어에 앱을 내면 **하루 1명 유입도 극히 어렵다.** 스토어는 내 앱을 홍보해주지 않는다.
> - 결국 외부 바이럴을 직접 하거나, 지인에게 부탁하거나, 유료 마케팅을 해야만 유입이 생긴다.
> - 앱인토스는 이보다 훨씬 용이하다 — 이 차이가 미니앱 생태계를 선택한 이유.

### 1.2 아이템 선정 — 8~10개를 만들며 얻은 결론

- 만든 앱이 **전부 잘 되지는 않았다.** "처음부터 완벽하게" 접근하면 오히려 잘 안 됐다.
- 정착한 방식: **일상의 불편(문제 정의) → 가벼운 앱부터.** 화면이 한두 개여도 괜찮다.
- 요즘은 개발 자체는 쉬워졌기 때문에, 오히려 **"뭘 만들지"(기획)에서 막히는 사람이 많다.**
- 결론: 거창한 아이디어보다 **내가 쓰고 싶은 앱을 먼저 만들어 아이디어를 검증**하는 것이 중요.

### 1.3 "인스타 언팔한 사람 찾기"는 오리지널 아이디어가 아니다

- 시중에 **이미 알려져 있던 기능**이었다. 다만 **앱인토스 생태계 안에는 비어 있었다.**
- "괜찮은 앱들을 보면서, 앱인토스에도 이런 게 있으면 좋겠네" 하고 넣어본 것. → **빈칸(공백 시장) 찾기 전략.**

### 1.4 완벽 vs 빠른 출시

- 개발하다 보면 "이것도 넣고 싶고 저것도 넣고 싶다"는 생각이 항상 든다.
- 그러나 **최소 기능만 충족되면 먼저 시장에 내놓는다.**
- 이유: **"이 앱을 쓸지 말지는 결국 유저가 정한다."**
- 사이클: **빠르게 개발 → 빠르게 마케팅 → 유저 반응 확인 → 반응이 좋으면 그때부터 본격 투자.**

### 1.5 제약을 기획의 무기로 — 서버 없는 앱

발표자가 인지한 제약:
1. iOS 개발자지만 **서버 개발 경험 없음**
2. **개인정보 이슈**가 한창 민감한 시기
3. **구현이 복잡하면 사람들이 안 쓸 것** 같음

→ 결론: **"안 되는 건 안 하겠다. 내가 할 수 있는 걸 하자."** → **서버 없는 앱**으로 설계.

**실제 동작 흐름 (자체 로그인 없음)**
1. 토스 앱에서 미니앱 진입
2. 유저가 **직접 인스타그램 앱**으로 이동해 본인 팔로워 데이터를 인스타그램에 요청
3. **약 10~15분 뒤** 인스타그램이 이메일로 팔로우 목록 파일 전송
4. 유저가 그 파일을 미니앱에 **업로드**
5. 앱이 비교·분석해 언팔 목록 표시

- 진행자 평: "슬릭하지 않고 번거로운 퍼널" → **이탈 가능성이 큰 구조.** (이 이탈을 어떻게 잡았는지가 5부의 핵심)

### 1.6 제작 시간과 출시 후 개선

- **순수 제작 10시간 / 달력 기준 3일.** "하루도 안 걸린 셈."
- **대신 출시 후 개선에 훨씬 긴 시간을 투자.**
- 콘솔 빌드 내역이 **20행 × 10페이지 = 약 200개.** 문구 하나까지 고치며 **직접 휴대폰으로 플로우를 타보고** 유저 관점을 점검.
- 점검 질문: *"유저가 이 문구를 봤을 때 직관적인가? 다음 화면으로 갈 수 있게 잘 안내하고 있나?"*

> **가장 강조된 문장**
> "출시하고 나서 '어, 반응이 없네' 하고 그만두는 경우가 제일 안타깝다. 개발까지는 쉽고 재밌지만, **출시 후 반복해서 보며 고쳐 나가는 것이 훨씬 더 중요하다.**"

## 2부. 개발 — "코드는 한 줄도 직접 안 썼다"

### 2.1 AI 위임 개발

- **"A B C D 한 글자도 안 적었다."** 전부 **한국어 지시**로 AI에 위임.
- 팀 규모의 변화: 예전에는 앱 하나 = **최소 4명, 많으면 10명**. 지금은 **1~2명이면 충분**.
- 일하는 방식이 **"직접 짜는 법" → "AI에게 잘 시키는 법"**으로 바뀌었고, 개인이 **여러 앱을 동시 운영**하는 경우도 생김.

### 2.2 제로 → 원 전체 흐름

```
① 앱인토스 MCP 세팅 (최초 1회)
   → ② 기획 → ③ 디자인(아이콘·썸네일) → ④ 개발 → ⑤ 출시
   → ⑥ 홍보·마케팅 ⇄ ⑦ 유지보수      ← 계속 반복되는 구간
```

- ①~⑤(출시까지)는 **AI가 거의 다 해준다.**
- ⑥·⑦은 **사람의 영역** — 감성·디테일이 필요한 홍보/마케팅, 유저 관찰과 피드백 반영, 지속 개선.

### 2.3 앱인토스 MCP

- **앱인토스 개발자 센터**에서 제공. 앱인토스에 대한 **지식을 전부 보유**.
- 설치하면 AI에게 "앱인토스가 뭔지, 출시는 어떻게 하는지, 빌드는 어떻게 하는지"를 전부 물어볼 수 있다.
- → **누구나 앱인토스 출시에 필요한 개념을 얻게 된다.**
- **단점: 토큰을 많이 먹는다.** (해결책은 2.6 참조)

### 2.4 사용 도구 — Claude + Codex, 월 5~6만 원

| 도구 | 용도 | 선택 이유 |
|---|---|---|
| **Claude** | **디자인** | 내부에 **Claude 디자인**이 있어 1차 시안을 뽑고 그걸로 개발 |
| **Codex** | **개발** | ① 머릿속 생각을 길게 다 적어 **대기 메시지로 쌓아둬도 관리가 쉽다** ② 모델 특성상 **엣지 케이스·디테일을 먼저 제안**하는 "참견형" |

- 요금제는 **각 3만 원 수준, 합계 월 5~6만 원.** 비싼 요금제 아님.
- **정답 없음**: 반대로 Codex/GPT로 디자인, Claude로 개발하는 사람도 있다. **둘 다 쓸 필요도 없고 하나만 써도 된다.** 직접 써보고 잘 맞는 쪽을 고를 것.
- "참견형"이 불편한 사람(시킨 것만 하길 원하는 사람)은 Codex를 선택하지 않아도 됨.

### 2.5 디자인 — TDS(토스 디자인 시스템)를 AI에 이식

발표자가 가장 어려워한 영역이 **디자인**. 해법:

1. **앱인토스 개발자 센터 → "디자인 도구"** 검색 (개발자 센터는 웹사이트, 구글에 "앱인토스 개발자 센터"로 검색 가능)
2. **TDS zip 파일 다운로드** → 압축 해제하면 **`.fig` = 피그마 파일**
   - 버튼·라벨·세그먼트 컨트롤 등 토스 컴포넌트가 모두 담겨 있음
3. 그 피그마 파일을 **Claude 디자인에 통째로 등록**
4. Claude가 **혼자 20~30분간 학습** → TDS가 뭔지 이해하고 자기 환경에 적용
5. 이후 **어떤 디자인을 시켜도 TDS 기반으로 화면을 산출** — 버튼 곡률, 두께, 배경색 등 세부 규칙까지 반영

- 결과: **"토스러운" 심플한 디자인**이 자연스럽게 나옴 (토스 개발자·프로덕트 디자이너가 다듬은 시스템을 그대로 활용).
- 필수는 아니지만 "토스처럼 쉽게 만들고 싶다"면 좋은 팁.

### 2.6 지식 관리 구조 — 토큰 절감의 핵심

```
앱인토스/                      ← 루트 폴더
├── platform-docs/            ← 앱인토스 공통 지식 전부 (광고·결제·배포 등 도메인 지식)
├── 프로젝트A/  └ PRD.md
├── 프로젝트B/  └ PRD.md
└── ...
```

- 배경: 앱을 여러 개 만들면 **같은 앱인토스 문서를 반복해서 참조**하게 된다.
- **MCP를 경유하는 것 자체가 토큰을 많이 소모** → 반복 시 비용이 아깝게 느껴짐.
- 해결: **앱인토스 지식을 platform-docs 폴더에 정리해두고 AI가 그걸 바라보게 한다.**
- 효과: MCP를 거치지 않아도 되므로 **토큰을 월등하게 절감**.

### 2.7 PRD — AI에게 주는 기획 정의서

**PRD란?** 거창한 게 아니라 **텍스트만 있는 기획 정의 문서.**

AI는 이 앱이 어떤 앱인지 모른다. PRD가 있으면 AI가 이해한다:
- 이 폴더에서 작업하는 이 앱은 "인스타 언팔 찾기"구나
- 화면은 이렇게 구성되어 있구나
- 주 연령층은 이렇구나
- 앞으로 해야 할 일은 이렇게 있구나

→ 한마디로 **"AI에게 시킬 문서의 지침".**

**PRD 작성법 (개발 경험이 없어도 가능)**

1. 구글에 **"PRD 스킬"** 검색 → 기획자들이 만들어둔 **템플릿 중 퀄리티 괜찮은 것**을 다운로드
2. AI에게 그 템플릿을 주고 **"인스타 언팔 앱 만들고 싶은데 PRD 적어줘"**
3. **맥북 마이크를 켜고 5분간 혼자 말한다** → 음성이 텍스트로 변환
   - 실제 말하는 방식: *"인스타 언팔로우를 찾아주는 앱을 만들고 싶다. 근데 내가 봤을 때는 이럴 것 같아. 유저들은 이런 걸 원할 것 같아…"* — **친구에게 얘기하듯 편하게, 두서없어도 됨**
4. AI가 두서없는 맥락을 **혼자 정리**하고, **"이건 넣을까요? 다음 버전으로 미룰까요?"**라고 되물으며 함께 완성

- **초기 PRD의 품질이 중요**: 잘 갖춰져 있어야 나중에 "이거 넣었나?", "다음에 넣으면 좋겠다" 같은 항목까지 정직하게 관리되고, **AI와 새 세션을 열 때도 계속 도움이 된다.**

### 2.8 "개발은 말로 하되" 반드시 챙길 3가지

| # | 항목 | 내용 |
|---|---|---|
| 1 | **QA는 내가 직접** | 개발은 AI가 했어도 **검증은 내가.** 버튼을 눌렀을 때 다음 화면으로 잘 넘어가는지, 결제 성공 시 내용이 제대로 보이는지 직접 확인 |
| 2 | **로그를 반드시 남기게 시킬 것** | *"다른 거 다 괜찮으니 로그를 꼭 같이 작성하라"*고 AI에 지시. 유저가 **어디서 이탈했는지**, **어떤 버튼을 자주 누르는지** 지표화 가능. 나중에 대시보드로 연결됨 |
| 3 | **출시해도 아무 일도 안 일어난다** | 출시는 끝이 아니라 시작. 일어나게 만들려면 3~5부의 활동이 필요 |

## 3부. 마케팅 — 노출을 만드는 3계층

### 3.1 실제 대시보드가 말해주는 성장 곡선

- **4월 런칭 → 초반 약 15일(보름)은 반응 거의 없음.** 이 시기가 **DAU 10명 목표 구간**.
  - 유입은 **전부 지인**. 지인들이 피드백을 줬고 그걸로 개선.
- 이후 **500명씩 갑자기 유입되는 스파이크** 발생 → **스마트 발송(광고성)** 때문.
- 이 스파이크를 조금씩 반복하면서 **평균 유입 자체를 계단식으로 끌어올림.**
- 출시 약 한 달 뒤 **누적 147만 명**.

### 3.2 노출을 만드는 3가지 계층

| 계층 | 설명 | 우선순위 |
|---|---|---|
| ① **앱인토스 자체 제공 기능** | 스마트 발송, 프로모션, 공유 리워드 등 — 별도 노력 없이도 플랫폼이 제공 | **집중** |
| ② **외부 채널 마케팅** | 인스타·스레드·틱톡·X·에브리타임 등 | **집중** |
| ③ **앱인토스 팀의 노출 확대** | 잘 되는 앱을 플랫폼이 더 노출시켜 줌 | 기대하고 시작할 대상은 아님 (①②의 결과로 따라옴) |

→ **선순환 구조**: ①②로 성과를 내면 → 플랫폼이 "사용자 가치가 있는 앱"으로 판단 → ③ 노출 확대 → 다시 성장.

### 3.3 앱인토스 제공 채널 상세 (모두 무료 또는 저비용)

#### ⓐ 스마트 발송 — 광고성
- 내 미니앱을 **한 번도 써본 적 없는 유저에게도** 토스 푸시 알림으로 노출
- **완전 무료** (토스/앱인토스 제공 기능)
- 실제 지표에서 **클릭 수 500회**가 나온 케이스 존재 → **"스마트 발송만 잘 써도 1,000명은 들어오게 할 수 있다"**
- 용도: **신규 유입** + 기존 사용자 **재방문 유도**

#### ⓑ 스마트 발송 — 기능성
- **앱 내 특정 이벤트 발생 시** 유저에게 알림 (예: "분석 결과 다 나왔어요")
- **유저 동의 기반 / 유저 행동 기반**이므로 갑작스러운 광고보다 **클릭률이 훨씬 높다**
- **역시 무료**

#### ⓒ 프로모션 (토스 포인트)
- 유저에게 **토스 포인트를 지급**하면서 내 앱을 홍보 (예: "팔로우 분석 결과를 보면 100원 드릴게요")
- **비즈머니를 충전**해서 운영
- **토스 앱 두 번째 탭인 '혜택' 탭에 광고 노출** → 자연스러운 유입 경로 확보

#### ⓓ 공유 리워드
- 토스에 **연락처를 연동**한 유저가 지인에게 "이런 앱이 있다"고 **토스 푸시 알림**을 보낼 수 있음
- 개발자는 **유저가 공유했는지 여부를 알 수 있다** → 공유를 조건으로 보상 설계 가능
- 실제 적용 예: **"공유하면 광고 안 보게 해줄게요"**, **"로또 번호 5개 추천 받기"**(원래 과금 기능을 공유 조건으로 제공)

#### ⓔ 공유 링크 OG 이미지 커스텀
- 미니앱 공유하기 링크에는 **메타데이터**가 담겨 있어 **미리보기 이미지를 직접 커스텀 가능**
- 기본 이미지 대신 **앱의 가치가 즉시 드러나는 이미지**로 교체 → 카카오톡 등에서 공유 시 전환율 상승
- 지인 공유, 스레드 홍보 등 모든 링크 공유 지점에 적용

#### ⓕ 리뷰 요청 — `requestReview`
- 앱인토스가 제공하는 메서드. 호출하면 **화면 이동 없이 현재 화면에서 바로 별점 입력** 가능
  - (기본 방식은 새 화면 이동 → 별점 → 보내기 → 이탈 부담이 큼)
- **타이밍이 핵심**: 유저가 **앱의 가치를 충분히 느꼈을 때, 기분이 좋을 때** 띄우면 5점을 주는 경우가 많다
- 결과: **리뷰 7,000개, 평점 4.5+** (초기에는 리뷰 100개 미만 + 평점도 낮았음)
- 배경 원리: **아무것도 안 하면 사람들은 좋을 때가 아니라 안 좋을 때 리뷰를 쓴다.**

### 3.4 외부 채널 마케팅

- **SNS 계정 1개 운영**: 인스타 `미니앱 스튜디오` — 앱이 8~10개이므로 **링크트리 웹사이트**를 만들어 전 앱 링크를 모아둠 (유저를 한곳에 모아 자연스럽게 앱으로 유도)
- **콘텐츠**: 게시물·릴스 제작. 도구는 **CapCut 구독**. *"엄청 잘 만들어야지"가 아니라 자연스럽고 간단하게.*
- **배포 채널**: 스레드, 인스타그램, 틱톡, **X(트위터)**, **에브리타임** 등
- **X의 화력**: 발표자가 올린 게 아니라 **제3자가 자발적으로 "토스에 이런 거 있더라"고 올린 게시물이 조회수 360만 돌파**
  - 6월 30일 게시물 → **7월 1일 검색 유입 약 2만 명** (평소 대비 폭증)
  - 이런 바이럴이 **2~3회** 있었음
  - 시사점: **초반 화력을 높여 끌어내면 유저가 관심을 가져준다** → 초기 확산에 집중할 가치가 있음
- **데이터 기반 채널 선택**: 앱인토스 콘솔 대시보드의 **연령 분포**를 보니 **10·20대가 가장 두꺼움**(인스타그램 사용자 구성 반영) → **10·20대가 모이는 커뮤니티(에브리타임 등)**에 집중 홍보
  - 진행자 정리: **"마케팅은 어렵게 생각할 게 아니라 상식적인 접근"**

### 3.5 대부분이 놓치는 지점

- 스마트 발송·프로모션까지는 많이들 쓴다.
- 그러나 **공유 리워드 / 공유 링크 이미지 커스텀 / 리뷰 요청 / 외부 채널**은 모르거나 "엄두가 안 난다"며 안 한다.
- **"한 번 해보는 것 자체가 어렵지, 해보면 쉽다."** 마케터가 아닌 iOS 개발자도 다 했다.

## 4부. 수익화 — 광고와 결제

### 4.1 출발점: 이탈 지표

- 로그 기반 퍼널 분석 결과 **결과 화면을 본 유저의 23%가 결제까지 전환**.
- 따라서 논리는 단순: **"결과 화면까지 최대한 많이 보내면 결제가 많이 일어난다."** → **이탈을 잡는 것이 곧 매출.**
- 퍼널상 **4단계 → 5단계 구간에서 이탈이 가장 컸다.** (해결은 5부)

### 4.2 광고 vs 인앱결제 판단 기준

| 모델 | 특징 | 적합한 경우 |
|---|---|---|
| **광고** | 진입 장벽이 낮아 **모든 유저가 쉽게 수용** | 결제까지 가긴 어렵지만 **반복 접속**하는 성격의 앱 |
| **인앱결제** | 정말 필요로 하는 유저만 결제 | **결제할 만한 가치를 명확히 돌려주는 앱**, BM이 확실할 때 |

- 광고 안에서도 **5초 광고 / 30초 광고**로 갈리고, 결제 안에서도 **단건 결제 / 정기 구독**으로 갈린다. → **앱 기획 특성에 맞춰 선택해야 한다.**
- "광고냐 결제냐"에 정답은 없다.
- 인스타 언팔 앱은 **둘 다 사용**: 결과를 보려면 **990원 결제**, 그 전에 **광고 노출**.

### 4.3 eCPM 실측치 (본인 앱 기준, 절대치 아님)

**eCPM = 광고가 1,000명에게 노출됐을 때 내 수익으로 얼마가 되는가**

| 광고 유형 | eCPM | 특성 |
|---|---|---|
| **문구형 배너** | **2,000원 초반** | 가장 가벼운 노출 |
| **전면형** | (배너와 리워드 사이) | **5초 후 스킵 가능** → 유튜브 5초 스킵처럼 **UX 훼손이 적다** |
| **리워드** | **약 3만 원** | **30초 이상** 시청 → 유저가 끝까지 볼지, **보상 체계가 납득되는지**가 관건 |

> ⚠️ 발표자·진행자 모두 강조: 이 수치는 **효준 님 미니앱의 사례**이며, **기간·지면·앱 기능에 따라 매우 유동적**이다. 참고치로만 볼 것.

**의사결정 과정 (실험의 가치)**
1. 처음에는 **전면형만** 사용 — 뒤에 결제가 있어 **UX를 해치면 안 된다**고 판단
2. 이것저것 **실험을 반복**하며 지표를 직접 측정 (로그 + 대시보드가 있었기 때문에 가능)
3. **"유저가 이 보상에 납득하는가"** 관점에서 자기 앱은 조건을 충족한다고 판단
4. 유저가 리워드 광고를 **끝까지 본다**는 것을 확인 → **리워드로 정착**, **eCPM이 훨씬 높은 광고를 가져감**

> **"시도를 안 했으면 놓칠 뻔한 차이."**

### 4.4 결제 전환을 높인 장치들

| 장치 | 내용 |
|---|---|
| **선택지 다양화** | 단순 "990원"이 아니라 **1개월 무료 체험 / 첫 결제 할인 / 재구독 할인** 등 제공 → **심리적 허들 낮춤** |
| **부분 공개(티저)** | 결과가 100명이면 **전부 보여주지 않고 일부만 공개** → 궁금하면 결제 |
| **단건 + 정기구독 동시 제시** | *"한 번 더 들어올 것 같은데 그냥 구독해버릴까?"* 라는 **멘탈 모델**을 유도 |
| **가격 실험** | 처음 **2,000원** → 팀원 피드백 *"2,000원은 절대 안 한다"* → **990원**(세 자리 수의 심리적 안정감)으로 시장에 내보고 유저 피드백으로 검증. *"논리적이지 않았지만 해보면서 맞춰가는 과정"* |

## 5부. 운영·리텐션 — 로그가 만든 결과

### 5.1 로그의 정의와 필요성

- **로그 = 유저가 내 앱에서 돌아다닌 흔적.** 버튼 클릭, 화면 조회, 5초 이상 체류 등 **정의하기 나름.**
- 핵심 이유: **유저는 "나 이제 앱 종료해요"라고 말해주지 않는다.** → 이동·클릭·노출을 **직접 정의해 로그로 심어야** 지표가 생긴다.
- 이 로그가 그대로 **퍼널 대시보드**가 되고, 개선 판단의 근거가 된다.

### 5.2 이탈 원인 진단 (4 → 5 구간)

로그로 확인된 실제 원인:
1. 토스 앱 → **인스타그램 앱으로 이동**해야 함
2. 인스타그램에 데이터 요청 → **응답까지 10~15분 소요**
3. 그동안 **유저가 잊어버린다** ("아 맞다, 나 신청했지")
4. 메일을 받아도 **알림이 없어서 잊는다**
5. → **앱으로 돌아오지 않는다**

### 5.3 해결책 ① — 기능성 푸시 알림 (15분 뒤 리마인드)

- 설계: **"15분 뒤에 알림을 보내 드릴게요, 받으시겠습니까?"** 동의를 받고, 이메일 도착 시점에 맞춰 푸시 발송
- **결과: 3만 명 발송 → 1만 명 이상 복귀 = 약 40%**
  - *"푸시 알림으로 40%면 정말 많이 나온 것"*
- **퍼널 개선 효과**
  - 해당 구간 전환율 **+14%p**
  - 최종 전환 **9% → 14% (+5%p)**
  - 앞 구간은 아무것도 바꾸지 않아 **전후 수치가 동일** → 푸시의 순효과임이 명확히 증명됨
- 이 개선은 결과 화면 도달 증가 → **23% 결제 전환**을 통해 매출로 직결

> **"데이터는 거짓말을 하지 않는다."** 페인 포인트를 대시보드로 찾아내고, 그 지점에만 정확히 손을 댄 사례.

### 5.4 해결책 ② — 재방문 이유 만들기 (주간 알림)

- 문제 제기(진행자): *"언팔한 사람 한 번 확인하고 나면 다시 들어올 이유가 있나?"* — 발표자도 **단건 결제로 끝날 앱**이라는 위기감을 느낌
- 해결: **주기적 기능성 알림** 도입
  - 문구: **"이번 주 팔로우 변화를 보실래요?"**
  - **타이밍 설계**: 유저가 여유로울 **토요일 오전** 등을 노려 발송
- **결과: 5만 발송 → 3만 클릭 = CTR 약 60%**

### 5.5 해결책 ③ — 유저 피드백 기반 기능 개선

- 리뷰에서 반복된 요구: *"지금 상태만 말고, **이전부터 언제 언팔했는지**, **기간별 팔로워 변화**, **새로 생긴 팔로워**도 보고 싶다"*
- 반영 → **계속 써야 할 이유**를 만들어 단건 결제형 앱을 **리텐션형 앱으로 전환**

### 5.6 해결책 ④ — 문의 응대 자동화

- 앱이 처음 터졌을 때 **시간당 약 50건**의 문의. 유저가 계속 들어오니 문의도 계속 증가.
- 견디며 응대하다 깨달음: **문의도 비슷하고 내 답변도 똑같다** → **자동화 가능**
- 구축 방식:
  1. **집에 안 쓰는 컴퓨터**를 상시 켜둠
  2. 그 로컬 PC에 **무료로 풀려 있는 AI**를 계속 띄워둠 (Codex·Claude 같은 유료 도구가 아님)
  3. 앱인토스로 문의가 들어오면 **문의 유형을 판별하고 자동으로 답변을 작성**
  4. 본인은 **보내기 버튼만 클릭**
- → 이 환경 덕분에 **본업을 유지하면서 여러 앱을 동시에 운영**할 수 있었음

### 5.7 여러 앱을 동시에 운영하는 3가지 팁

| # | 팁 | 이유 |
|---|---|---|
| 1 | **공통 지식은 한 곳에서 관리** | 앱인토스 개발 내용은 결국 다 비슷하다. 지식이 한 곳에 있으면 따로 명령하지 않아도 AI가 올바른 방향을 잡는다 |
| 2 | **PRD로 개발 범위를 잠근다** | AI는 시키지 않은 것도 할 수 있다. PRD로 **범위를 명확히 가이드**해야 한다 |
| 3 | **운영은 최대한 자동화 + 지표는 반드시 만든다** | 대시보드가 있어야 **전환율·클릭률**을 볼 수 있다 |

## 6. 웨비나를 관통하는 메시지

> **"엄청나게 갖춰서 출시하려 할 필요 없다.
> 문제 정의를 빠르게 하고, 개발도 빠르게 하고, 마케팅도 해보고,
> 반응이 좋으면 계속하고, 아니면 다른 걸로 다시 도전하면 된다.
> **일단 먼저 해보는 것**, 그리고 이 과정을 **빠르게 전환**하는 것이 중요하다."**

**요약 원칙 5가지**
1. **작게 시작한다** — 화면 1~2개, DAU 10명 목표부터
2. **빈칸을 찾는다** — 오리지널이 아니어도 된다. 생태계에 없으면 기회다
3. **제약을 설계로 바꾼다** — 서버를 못 만들면 서버 없는 앱을 만든다
4. **출시는 시작이다** — 200번 고치고, 로그를 심고, 지표로 페인 포인트를 찾는다
5. **플랫폼이 주는 무료 도구를 끝까지 쓴다** — 스마트 발송·프로모션·공유 리워드·리뷰 요청·OG 이미지

## 7. 실행 체크리스트 (이 영상에서 바로 가져갈 것)

**출시 전**
- [ ] 앱인토스 개발자 센터 → **MCP 설치** (최초 1회)
- [ ] `platform-docs/` 폴더에 **앱인토스 지식 정리** (MCP 토큰 절감)
- [ ] "PRD 스킬" 템플릿 확보 → **음성 5분 → AI 정리**로 PRD 작성
- [ ] 개발자 센터 → **디자인 도구 → TDS zip → `.fig`** → Claude 디자인에 등록(20~30분 학습)
- [ ] AI에 개발 지시할 때 **"로그를 반드시 함께 심어라"** 명시
- [ ] **QA는 직접** — 실제 단말로 전체 플로우 주파

**출시 직후**
- [ ] **스마트 발송(광고성)** 으로 신규 유입 만들기 (무료)
- [ ] **공유 링크 OG 이미지 커스텀**
- [ ] **`requestReview`** 를 "유저가 만족한 순간"에 호출
- [ ] 지인 배포 → 초기 피드백 수집

**성장 단계**
- [ ] 대시보드에서 **최대 이탈 구간** 찾기
- [ ] 그 구간에 **기능성 푸시** 투입 (동의 기반)
- [ ] **재방문 이유**가 되는 주기적 알림 설계 (요일·시간대까지)
- [ ] **프로모션(토스 포인트)** + **공유 리워드** 도입
- [ ] 대시보드 **연령 분포** 확인 → 해당 층이 모인 외부 커뮤니티 공략
- [ ] 광고 유형 **A/B 실험** (전면형 ↔ 리워드), eCPM으로 비교
- [ ] 결제 **선택지 다양화**(무료 체험·할인·구독) + **부분 공개**
- [ ] 문의가 늘면 **응대 자동화**
