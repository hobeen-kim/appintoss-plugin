# 토스 UX 라이팅·그래픽·해상도 기준

미니앱 화면에 들어가는 **모든 문구**와 그래픽, 화면 설계 해상도의 기준이다. 공홈 UI/UX 가이드(`design/consumer-ux-guide`)에서 정리했다. 검수 반려 사유가 되는 항목이 섞여 있으므로 문구를 쓸 때마다 이 기준을 적용한다.

## 1. UX 라이팅 5원칙

### ① 해요체
제품 안의 **모든 문구를 '해요체'로** 쓴다. 상황·맥락 불문이다. ("확인하십시오" ✗ → "확인해 주세요" ✓)

### ② 능동적 말하기
수동형 대신 능동형을 쓴다.
- 됐어요 → 했어요
- '~었' 빼기 ("저장되었어요" → "저장했어요")
- 동사를 바꿔 쓴다

**수동형이 더 나은 예외**: 서비스 종료·기간 만료(주어 강조), 사용자에게 미치는 영향의 인과 설명(연체·해지·적용), 민감한 안내에서 사용자를 안심시킬 때. 단 주기적으로 종료가 반복되는 제품에는 "종료돼요"를 쓰지 않는다.
**표기**: `되어요` ✗ → `돼요` ✓ (좁은 모바일 화면 고려)

### ③ 긍정적 말하기
"안 돼요", "없어요" 대신 "~하면 할 수 있어요"로 쓴다.

> **다이얼로그 왼쪽 버튼은 [닫기]로 통일한다.** "취소"는 사용자가 하던 작업이 취소된다고 오해할 수 있어 쓰지 않는다.

**부정형이 필요한 예외**: 정책상 서비스를 쓸 수 없을 때(이유를 함께), 일부 기능만 쓸 수 없을 때, 정보 수집 안내처럼 사용자를 안심시켜야 할 때.

### ④ 캐주얼한 경어
'~시겠어요?', '~시나요?', '~께' 같은 과도한 경어를 쓰지 않는다.
- 동사에서 '~시' 빼기 / '계시다' → '있다' / '여쭈다' → '확인하다·묻다' / '께' → '에게'
- 경어를 뺐을 때 어색하면, **파악하려는 정보를 주어로 삼아** 문장을 새로 쓴다.

**경어 예외**: 사용자의 맥락을 활용해 질문할 때, 사용자의 상황을 추정할 때, 설문처럼 선의를 기대할 때 '시나요?/셨나요?'를 제한적으로 쓸 수 있다.

### ⑤ '{명사} + {명사}' 쓰지 않기
한자어 명사를 풀어서 동사 형태로 쓴다. 풀기 어려우면 '{명사}가 {명사}해서' 형태로만 바꿔도 훨씬 캐주얼해진다.

### 그 밖의 문구 규칙 (검수 항목)
- 비속어·은어·과도한 유행어 금지
- **CTA는 눌렀을 때 무슨 일이 일어나는지 예측 가능해야 한다.** 화면에서 이미 설명한 가치를 CTA에 반복하지 않는다. CTA 위에 과장된 보조 설명을 덧붙이지 않는다.
- 사용자 안내·확인이 필요하면 TDS 모달을 쓴다

## 2. 그래픽 사용 기준

### 토스 제공 리소스
- 아이콘·이모지 약 7,000종을 앱빌더·피그마에서 쓸 수 있다.
- **아이콘은 화면에서 24~40px로** 쓴다. 아이콘·이모지를 2개 이상 병렬 조합하지 않는다(한 번에 하나).
- **토스 제공 리소스는 서비스 화면 내 UI 용도로만** 쓸 수 있다. **앱 로고·썸네일 등 앱 정보에는 쓸 수 없다(2차 가공 포함).**
- 스마트폰 목업은 제공 파일을 그대로 쓴다(크롭·색보정·왜곡 금지). 개발 시에는 URL 참조를 권장한다: `https://static.toss.im/illusts/mockup-template-250508.png` 등.
- 3D 그래픽·애니메이션은 토스가 제공한 모듈에 포함된 리소스만 쓸 수 있다.
- 토스 그래픽 자산은 비바리퍼블리카의 지식재산권이며, 앱인토스 제휴 환경 내 운영·홍보 목적으로만 사용할 수 있다.

### 올바른 사용법 7가지
1. 문맥에 맞는 그래픽을 쓴다(장식이 아니라 이해를 돕는 역할).
2. 정보 밀도에 맞는 크기 — 단순한 그래픽은 작게, 디테일이 많으면 충분히 크게.
3. 한 화면에 그래픽을 많이 쓰지 않는다 — 핵심 하나만, 나머지는 아이콘으로.
4. 핵심 정보를 가리지 않게 배치한다(불필요한 스크롤 유발 금지).
5. **부정적이거나 호소·애원하는 감정 표현 금지 — 다크 패턴에 해당한다.**
6. 장식적 이펙트(의미 없는 묘사·파티클·과한 그라데이션) 금지.
7. 상황을 정확히 전달한다(오류가 아닌데 느낌표, 기다릴 필요 없는데 로딩 애니메이션 금지).

### 직접 제작할 때
토스 스타일(단순·명료·깨끗한 디지털 그래픽)을 지킨다. 손그림·서정적 화풍·만화적 표현은 이질적이다. 고화질로 만들고, 라이트·다크 모드 모두에서 보이도록 중간 명도를 쓰며, 화면 전체 컬러·레이아웃과 균형을 맞춘다. 모노톤 과다·뿌옇고 칙칙한 인상은 피한다.

## 3. 해상도 설계 기준

기기별 대응이 아니라 **기준 해상도 하나를 정하고 스케일링으로 대응**한다.

- **논리 해상도(권장)**: 세로형 약 **360×640 ~ 420×740**, 가로형 약 640×360 ~ 740×420 중 **하나만** 고른다.
- **에셋 해상도**: **1x + 2x** 두 그룹이면 대부분 충분하다. 품질이 특히 중요할 때만 3x를 선택적으로 추가한다.
- 실제 트래픽의 70~80%가 가로 800~900 / 세로 360~420 viewport에 몰려 있다.
- 테스트는 대표 기기 3~5종이면 충분하다 — 화면 비율이 다른 2~3종 + Safe Area가 큰 1종 + 작은 화면 1종.

**권장하지 않는 방식**: 기기 모델별로 다른 논리 해상도 사용, 실제 픽셀 해상도 기준 좌표 계산, 과도한 에셋 해상도 그룹, 해상도마다 다른 레이아웃.

> 콘솔 제출용 스크린샷 규격(세로 636×1048)은 **에셋 규격**이지 설계 기준이 아니다. 캡처는 viewport 318×524 @2x로 맞춘다(`ait-assets`).

**게임은 풀스크린이 필수**다 — 콘텐츠가 화면을 꽉 채우고, 웹뷰 여백·반투명 영역·레터박스가 없어야 하며, 노치·카메라 홀·Dynamic Island는 Safe Area로 처리한다.
