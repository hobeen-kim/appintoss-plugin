# 버그 리포트 (플러그인 이슈 자동 발행)

플러그인 자체의 결함을 감지하면 표준 양식으로 이슈 초안을 작성해 사용자에게 보여주고, **승인 후에만** `hobeen-kim/appintoss-plugin`에 GitHub 이슈를 발행한다. 자동 감지하더라도 발행은 절대 자동으로 하지 않는다.

## 1. 언제 발동

다음 신호 중 하나를 감지하면 이슈 초안 작성을 제안한다:

- (a) **동일 게이트 3회 이상 반려** — pipeline 게이트가 같은 사유로 반복 반려될 때
- (b) **에이전트/스크립트 예외·비정상 종료 반복** — 같은 에이전트·스크립트가 반복적으로 실패할 때
- (c) **비공식 콘솔 API 응답 드리프트** — dom-map·스크립트가 기대하는 스펙과 실제 응답 불일치 (예: errorCode 변화, HTTP 상태 변화, 필드 구조 변경)
- (d) **문서와 실제 동작 불일치** — 공홈/dom-map 문서가 기술한 동작과 실제 콘솔·SDK 동작이 다를 때
- (e) **사용자 명시 요청** — "이거 버그야", "버그 리포트", "이슈 발행" 등

**제외(노이즈 금지)**: 사소한 일회성 오류, 네트워크 일시 장애, 사용자 입력 실수는 발동하지 않는다.

## 2. 수집 정보 (양식)

이슈 본문은 아래 항목을 채운다:

| 항목 | 내용 |
|------|------|
| 증상 | 1~2줄 요약 |
| 재현 절차 | 번호 매긴 단계 |
| 기대 동작 | 원래 어떻게 동작해야 하는지 |
| 실제 동작 | 실제로 무엇이 일어났는지 |
| 환경 | 플러그인 version(`.claude-plugin/plugin.json`), OS, 관련 스킬·커맨드, ait SDK 버전(있으면) |
| 로그·증거 | 에러 원문·grep 결과·종료코드 — **자격증명·토큰·쿠키·API키는 마스킹 필수** |
| 추정 원인·범위 | 의심 파일/스킬/스크립트와 영향 범위 |
| 심각도 | blocker / major / minor |

## 3. 중복 점검

발행 전 반드시 유사 이슈를 검색한다:

```bash
gh issue list --repo hobeen-kim/appintoss-plugin --search "<핵심키워드>" --state all
```

유사 이슈가 있으면 새 이슈를 만들지 말고, 해당 이슈에 코멘트 추가를 제안한다 (`gh issue comment <번호> --repo hobeen-kim/appintoss-plugin --body ...`).

## 4. 초안 제시 → 승인

채팅에 이슈 **제목·본문·라벨** 초안 전문을 보여주고 "이대로 발행할까요?"라고 묻는다. **사용자 승인 전에는 절대 발행하지 않는다.** 사용자가 수정을 요청하면 초안을 고친 뒤 다시 승인을 받는다.

## 5. 발행

승인을 받으면 본문을 임시 파일로 저장 후 발행한다:

```bash
gh issue create --repo hobeen-kim/appintoss-plugin --title "..." --body-file <tmp> --label bug
```

- `bug` 라벨이 없어 실패하면 라벨 없이 재시도하거나 라벨 생성 후 발행
- 발행 후 **이슈 URL을 보고**한다
- 실패 시(gh 미인증, 권한 부족 등) 사유를 그대로 보고하고 수동 발행 절차를 안내한다

## 6. 보안 규칙

- 이슈 본문에 **토큰/API키/쿠키/자격증명/PII 절대 포함 금지** — 로그 인용 시 해당 부분을 `***MASKED***`로 치환
- 경로의 사용자명 등 개인 식별 정보도 일반화 권장 (예: `/Users/<user>/...`)
